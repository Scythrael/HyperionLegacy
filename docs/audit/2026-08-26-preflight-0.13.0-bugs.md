# Combat 1.0 / 0.13.0 pre-debut bug log

Collected before the prod promotion. Two sources: **(A) user-reported** during device testing, and **(B) the multi-agent code audit** (15 area-auditors + adversarial verification). Nothing here is fixed yet by policy: gather everything, triage, agree a plan, THEN fix, before 0.13.0 ships.

Severity: critical (data loss / crash / softlock) > high (wrong result, reachable) > medium (visible defect, workaround exists) > low (cosmetic / edge).

---

## A. User-reported (device testing, 2026-08-26)

### BUG-U1 — Crafted combat gear invisible in the Logistics -> Ship Equipment warehouse tab
- **Severity:** medium (display only; items are SAFE and still installable via the ship-systems equip picker, so no data loss).
- **Scope:** weapons, shield emitters, hull plating, AND drone pods all missing. Economy systems (cargo bay / FTL / reactor / prospecting rig) show correctly.
- **Root cause (confirmed):** `BAY_SLOT_ORDER` (App.svelte:2822) = `["cargoBay","ftlDrive","reactorCore","specUtility"]` — the four ECONOMY slots only. `baySystemGroups` groups spares by that list, so any piece whose slotType is `weapon` / `shieldEmitters` / `hullPlating` / `droneBay` is filtered out of the display. The warehouse tab predates combat gear and never had the combat slots added.
- **Suggested fix:** add the four combat slots to `BAY_SLOT_ORDER` (order TBD). Then VERIFY: (1) the Salvage Bay (same `baySystemGroups`) salvages/destroys crafted combat gear correctly (weapon/drone blueprints carry recipes, so material refund should work — confirm salvageEquipment does not assume equipmentOutput); (2) combat Standard-Issue baselines that were uninstalled (pooled) render + destroy cleanly here. NOTE: this ties into AUDIT-2 (salvageEquipment predicate) — fix them together.

### BUG-U2 — Stale "Weapons — coming soon" reserved placeholder
- **Severity:** low.
- **Detail:** the Logistics warehouse shows a reserved "Finished Goods" family row (`LOGISTICS_RESERVED_GOODS`, App.svelte ~6887) marking Weapons / Modules / Consumables as "coming soon (combat)". Weapons are now craftable + real, so the Weapons marker is stale/contradictory.
- **Suggested fix:** drop "Weapons" from the reserved list (Modules + Consumables stay reserved). Ties to BUG-U1.

### BALANCE-U3 — Per-hull crafted-defense crossover (symptom of U6; 0.16.0)
- **Severity:** n/a (balance). Symptom of the U6 root.
- **Detail:** the Standard-Issue defensive floor is PER-HULL (freighter shield 200 / plating 400; carrier shield 500 / plating **880**). The interim `CRAFTED_DEFENSE_IMPLICIT_MULT = 10` (47e81b9) makes crafted defense reachable on small/mid hulls and carrier SHIELDS (crossover ~iLvl 33), but carrier PLATING needs ~iLvl 48 to cross 880, ABOVE the tier-2 iLevel cap of 40, so crafted plating stays underwater on the carrier (observed: crafted 90-110 hullStrength vs SI 880). Confirmed NOT a regression: SI floors are the hulls' authored SHIP_TYPES values (model.ts:767/879), untouched.

### LEAD-U4 — Ship-construction armor-seeding path (user hypothesis) — CLEARED
- **Status:** investigation lead, cleared. Two separate armor sources: SI plating (880) is seeded at SHIP CONSTRUCTION (installMissingCombatBaselines / seedCombatStandardIssueForShip = hull's authored hullStrength, correct); the crafted 90-110 plates are FABRICATOR output (iLevel-scaled, the U3/U6 issue), not construction. The `model-logic` + `tick-second-half` auditors swept both paths and found no construction mis-seed. Not coupled; no bug here.

### BUG-U5 — Cross-hull Standard-Issue defense transfer exploit (symptom of U6, high)
- **Severity:** HIGH (reachable balance exploit). Symptom of the U6 root.
- **Exploit:** SI combat baselines carry the SOURCE hull's full authored defense (per-hull; carrier plating 880 / shield 500). Combat slots are allow-empty with POOLABLE baselines (Unit 1.8a), and canFitEquipment does not hull-lock a baseline. So: build a carrier -> uninstall its 880 plating -> install on a freighter -> that freighter fields 980 effective hull vs its authored 500. Any multi-hull player migrates the strongest SI defense onto a favored hull. Shields identical.
- **Reachable:** yes, once the player has >1 hull type (destroyer 480 -> freighter 400 is already an upgrade with the starter-ish hulls).
- **NOT a regression:** combat baselines were poolable/transferable since Unit 1.8a; this session's allow-empty work was on ECONOMY slots. Pre-existing.

### BUG-U6 — ROOT: SI baseline = "full hull defense" (design; parent of U3 + U5)
- **Severity:** high (design root; combat-defense model). U3 and U5 are SYMPTOMS.
- **User design principle (verbatim intent):** "The first crafted armor should be right around standard-issue levels of power." A first crafted piece = a SIDEGRADE to SI, then improves; not a rounding error beside it.
- **Root cause:** Unit 1.4 (behavior-preserving bridge fold) made the SI combat baseline carry the hull's ENTIRE authored defense (plating hullStrength = hullIntegrity - frameHp; shield = hull shieldCapacity). Per-hull and LARGE. This one decision produces: (1) crafting floor absurdly high -> crafted gear feels useless; (2) floor unreachable within tier-2 iLevel-40 cap -> U3; (3) a huge transferable SI item -> U5.
- **Why tuning can't fix it:** no `CRAFTED_DEFENSE_IMPLICIT_MULT` value resolves it (big enough for carrier 880 makes freighter crafted gear absurd; does nothing for the transfer exploit).
- **Fix direction (architectural, re-baselines combat):** move the hull's defensive BULK to INTRINSIC hull stats, make SI gear a MODEST floor at ~first-crafted power. Then crafting starts at parity + scales (principle satisfied); SI ships stay viable off intrinsic hull defense; no large transferable SI item (kills U5); crafted defense reachable (kills U3). SHIFTS parity + balance fixtures + enemy tuning -> a combat-defense rework.
- **Scope call for triage:** 0.16.0 combat-defense rework, OR pulled earlier if judged a 0.13.0 debut blocker. The interim mult=10 (47e81b9) stays a stopgap until this lands.

## B. Multi-agent code audit findings (2026-08-26)

Coverage: **15 area-auditors** (save/migrations, equipment+salvage, tick x2, model x2, itemgen, combat-core, combat-mechanics, combat-patrol/parity, combat-readouts, App.svelte x2, combat/ship UI, misc UI). **12 areas returned clean.** 4 candidates surfaced; each was handed to an adversarial verifier. **2 CONFIRMED**, 2 refuted (real code inconsistencies but not reachable — kept below as hardening). ~2.5M subagent tokens, 19 agents.

### AUDIT-1 — First-wave durability seed ignores installed gear (bridge.ts:467, HIGH, CONFIRMED)
- **Category:** correctness / gear-durability. **Directly undermines the crafted-weapon loop** the user is testing.
- **Bug:** `defaultSystemDurabilityForHull` builds its seed combatant via `shipToCombatant(...)` with NO `installedGear`, so it takes the hull-default path: every weapon is a quality-0 `makeWeaponInstance` with `durabilityMax = 100`. That `[100,100,...]` seed is persisted as the FIRST-wave carry-state (tick.ts:3204 freshPatrolMission; patrolReplay.ts:432 replayPatrol). But the real wave-1 combatant is built WITH installed gear, where a crafted quality>0 weapon has `durabilityMax` up to 200 (q5). `applyCarriedSystemDurability` (patrolWave.ts:119) then clamps the real weapon's durability to the seed (100), so a q5 weapon opens at 100/200 = 50% <= the 60% DEGRADED threshold -> fights the WHOLE patrol at 75% damage (`DEGRADED_WEAPON_DAMAGE_PERCENT`) from wave 1. Strictly worse than a free q0 Standard-Issue weapon (opens 100/100 full). **Inverts the crafting reward gradient** (q0 fine, q4=55.6% degraded, q5=50% degraded).
- **Parity-safe:** symmetric across live + replay (both use the same seed fn), so combat parity is preserved; this is a gameplay-correctness defect, not a parity break.
- **Corroboration:** the ADJACENT `playerDrones` field (tick.ts:3198) WAS threaded with installedGear in Unit 2.3b; `playerSystemDurability` one line below was left on the hull-default path — the gear-threading fix was applied to drones and missed for durability.
- **Suggested fix:** thread the ship's `installedGear` into `defaultSystemDurabilityForHull` and its seed `shipToCombatant` call, so the seed's per-weapon `durabilityMax` (and count/order) match the real geared combatant; both callers (tick.ts, patrolReplay.ts) already hold `installedGear`. Then the wave-1 clamp is a no-op (full). Re-run parity + full suite after.

### AUDIT-2 — salvageEquipment destroy-branch uses blueprintKey===null, not isStandardIssueBaseline (salvage.ts:212, low, CONFIRMED)
- **Category:** silent-data-loss (latent). Same class as the data-loss bugs fixed this session; this destroy site was missed.
- **Bug:** `salvageEquipment` treats ANY spare with `blueprintKey === null` as a worthless SI baseline and destroys it for zero reward (`recovered={}`). The strict `isStandardIssueBaseline` predicate (model.ts, `blueprintKey null AND rarity 'standard'`) exists precisely to guard this, and the SIBLING `salvageShip` in the same file already uses it (salvage.ts:496/499) — `salvageEquipment` was missed. A dev-granted radiant iL-400 spare (`devGrantEquipment` mints blueprintKey null + rarity radiant, App.svelte:2532) matches this branch and is silently destroyed for nothing.
- **Reachability:** DEV_MODE / Vercel-Preview / local builds only today (DEV_MODE off in shipped prod, so no null-blueprint non-standard item exists for a normal player) — hence low severity. But it destroys the developer's highest-value test gear, contradicts the documented per-site invariant, and becomes live item deletion the moment any non-dev null-blueprint item source (loot/event) is added.
- **Suggested fix:** drop-in — replace `if (piece.blueprintKey === null)` at salvage.ts:212 with `if (isStandardIssueBaseline(piece))` (already imported at salvage.ts:49).

### AUDIT-3 (hardening, refuted) — unfitEquipment (dev slot-based) uses blueprintKey===null (equipment.ts:471)
- **Verdict:** verifier confirmed=false — the predicate inconsistency is REAL but the wrong outcome is NOT reachable by a production player (the dev slot-based `unfitEquipment` is dev-harness only). Kept as defense-in-depth: align it to `isStandardIssueBaseline` so every baseline-classifying site uses the one strict predicate (no per-site drift). Low/hygiene.

### AUDIT-4 (hardening, refuted) — cloneParticipants shallow-copies statusEffects (resolveBattle.ts:257)
- **Verdict:** verifier confirmed=false — `cloneParticipants` does `statusEffects: [...c.statusEffects]` (fresh array over the SAME element objects), and `tickEffects` mutates those instances in place; mechanically real but NOT reachable as a wrong outcome in any shipping path (no caller re-reads the pre-clone effect objects after the sim mutates them). Kept as a purity smell / future-safety item: deep-copy the effect instances in the clone so a future caller can't be silently corrupted. Low/hygiene.
