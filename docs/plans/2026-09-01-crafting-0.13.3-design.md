## 1. Why

Three problems, one release.

1. **There is no queue.** Every facility is strictly one-shot per slot. A refine line that finishes a batch clears itself and the slot sits idle until the player opens the console and reconfigures it. A fabricate order cannot be lined up behind the running one. This is the single largest source of "go back and click the thing again" friction in the game, and it is the exact opposite of [[feedback_build_ease_of_use_sell_peace]].
2. **Crafting progression is flat and opaque.** Crafting XP today is `CRAFTING_XP_PER_DURATION_TICK (=2) * durationTicks` for `refineJob | fabricateJob | shipBuild` (tick.ts `PROCESS_XP_AWARDS` ~691). Because the award is purely time proportional, **every job earns the identical 2 XP per tick regardless of what it produces**: a 12 tick ore refine earns exactly the same per unit time as a 300 tick tier-2 equipment craft. Add a queue (this release's own headline feature) and bulk refining becomes trivially sustainable, so the flat rate turns straight into the user's named failure case: "refining thousands of bars" driving iLevel. Nothing in the UI shows the player what crafting level even does.
3. **Crafting UX debt.** Six consoles (Refinery, Fabricator, Research, Fuel Depot, Warehouse, Salvage Bay) accreted independently across five releases. They share concepts (slot cards, configurators, upgrade rungs, disabled reasons) but not technique: emoji glyphs, `rgba()` tints, inline confirm patterns, and no attention dots on the dashboard cards even though the per facility signal already exists.

Salvage sits across all three: it is instant, it is the only production-shaped action outside the tick engine, and it is where loot clutter accumulates fastest.

## 2. Scope

**In:**

- A **universal, talent gated queue engine** over the existing `activeProcesses` / `TimedProcessKind` model, with per facility start adapters. UI exposed this release on **Refinery, Fabricator, Salvage Bay**.
- A new **Fleet Admiral talent chain** granting queue depth (the "RAM is expensive" model), mirroring the existing `unlockCaptainSlot` / `fleetLogisticsSlot1/2/3` pattern.
- **Salvage converted to a timed, queueable process**: new `TimedProcessKind`, new `ProcessEffect`, loot roll moved onto the seeded rng inside `resolveProcesses`, the grep guard rewritten to defend the real invariant.
- **Auto-salvage rules** (opt in, default off, in the save because they run offline).
- The **crafting level / iLevel redesign**: recipe value weighted XP, a gentle then steep curve, a decision on `faTalentBonus` / `achievementBoost`, and how the per tier iLevel cap interacts.
- The **crafting UX/UI pass** across all Facilities consoles: shared `<Icon>` component, `color-mix` tint standard, the 0.13.2 action modal pattern, per card attention dots on the Facilities dashboard, and a conscious carry-forward decision on every affordance in section 1 of the preservation inventory.

**Out (explicit non-goals):**

- **Queue UI for Research, Fuel Depot, Shipyard, Warehouse and Docks.** The engine is built to take them (adapters are a compile checked table), but their consoles get no queue controls this release. Staged fast follows, most naturally in 0.13.4. Reason: each one needs its own affordance decisions (a research queue has to reconcile with the tier grouping; a shipyard queue has to reconcile with "ship builds have no cancel"), and this release is already the biggest of the series.
- **Facility upgrade queues** (the SUGGESTIONS "queue BUILD orders" extension). Same reason. Engine ready, UI deferred.
- **The global readability / type scale pass.** That is 0.13.5 and it re-tunes every screen at once. 0.13.3 builds at the current px scale and does not invent a competing one.
- **The 6 template tooltip system.** Still unslotted. 0.13.3 keeps tooltips display only and reuses what exists.
- **Bulk emoji to SVG migration.** New icons are SVG through the new component; existing emoji migrate only on surfaces this release already rewrites.
- **Any combat or mission change.** No new gameplay outside crafting.
- **Recomputing existing crafting levels** under the new XP weights. Grandfathered.

## 4. Code grounding (what exists, what changes)

Anchors are current tip line numbers on `feat/crafting-0.13.3`. They drift: re-locate by content before editing.

**The process engine (unchanged shape, extended):**

- `startProcess(state, kind, inputs, durationTicks, effect, lineId?)` (`tick.ts:3942`): gate on inputs, atomic deduct at start, push a `TimedProcess`, mint `proc-N` from `nextProcessId`. Same reference no-op on failure. The optional `lineId` is attached by conditional spread so a non line process carries no key at all.
- `resolveProcesses(state, ticksElapsed, rng)` (`tick.ts:6586`): decrements every countdown, completes anything at or below `MISSION_TICK_EPSILON`, applies the effect, drops the process, returns `{ next, fleetAdminXpDelta, craftingXpDelta }`. Survivors are rebuilt **in original order**, which is what the deep equal parity test compares.
- `TimedProcessKind` (`model.ts:2121`) is a 9 member string union; `ProcessEffect` (`model.ts:2126` onward) is an 9 member discriminated union; `TimedProcess` (`model.ts:2213`) carries `id / kind / remainingTicks / durationTicks / effect / lineId?`.
- `PROCESS_XP_AWARDS` (`tick.ts:691`) is a `Record<TimedProcessKind, {fleetAdmin, crafting}>`, deliberately **exhaustive**: adding a kind without a row is a compile error. This is the mechanism that forces the new salvage kind to declare both axes.

**The per tick auto-start seam (this is the load bearing precedent for the queue):**

- `economyTick` runs `resolveProcesses` (`tick.ts:2833`) then, at its tail and **once per call**, `processRefineLines` (`:2850`), `processFabricateLines` (`:2860`), `processFuelPipelines` (`:2873`), `processShipRepairs` (`:2885`).
- `tick()` (`tick.ts:2956`) steps offline catch-up as `for (i < wholeSteps) economyTick(next, 1, rng)` plus one trailing fractional call. **Offline advances one whole tick at a time.** This is why an auto-start pass that runs once per `economyTick` call is already offline safe, and it is exactly where the queue promotion pass belongs.
- The known legacy precision note in `tick()` (`~2979-2996`) documents that the trailing fractional call fires those once per call passes one extra time on a sub-tick span. The queue pass inherits that same bounded artifact and must not make it worse.

**The craft line engine (refine + fabricate only):**

- `CraftLine` / `CraftLineMode` / `lineInputsPerIteration` / `allocatedItem` / `freeItem` / `freeItemForState` (`allocation.ts:44-198`). Allocation is **derived, never stored**: `allocated(item) = sum over active lines of remaining x inputsPerIteration`, `free = max(0, total - allocated)`. Only NOT-YET-STARTED iterations count, because an in-flight job already consumed its inputs at start.
- `stepCraftLine` (`tick.ts:5587`): one in-flight job per line (matched by `lineId`), a batch line at `remaining <= 0` is removed, an output at warehouse cap stalls the line (equipment blueprints exempt), otherwise it calls `startProcess` directly and decrements `remaining` + `mode.remaining` in one construction. A blocked line **survives unchanged and retries next tick**. That is the pause/auto-resume precedent the queue inherits verbatim.
- `canStartLine` (`tick.ts:5811`) is the single consolidated gate with a typed `StartLineBlockReason` union and a deliberate gate order; `maxAffordableIterations` (`tick.ts:5719`) is the affordable-now cap the configurator clamps to. `startLine` is a thin wrapper over `canStartLine`.
- **Only refine + fabricate ride this engine.** Research, fuel, ship build, ship repair, facility upgrades, equipment storage and docks each have their own start logic writing into one flat `activeProcesses`.

**Crafting level and iLevel:**

- `CRAFTING_XP_PER_DURATION_TICK = 2` and `craftingXpForNext(level) = 500 * level^2` (`model.ts:5421`, `:5433`), both flagged first pass tunable.
- `applyCraftingXp` (`tick.ts:2162`) folds the delta through the shared `foldXpLevelUps`, structurally identical to `applyFleetAdminXp`, with the same `MAX_LEVEL_UPS_PER_TICK` backlog guard.
- `computeItemLevel({craftingLevel, achievementBoost, faTalentBonus, itemTierCap})` (`itemgen.ts:179`) is `Math.min(sum, cap)`; `EQUIPMENT_ILEVEL_CAP_PER_TIER = 20` (`itemgen.ts:74`) makes `itemTierCap = blueprint.tier * 20`. Both bonus hooks are **hardcoded 0** at all three mint sites in `resolveProcesses`.
- **Recipe data reality:** `BlueprintDef` carries `tier` (`model.ts:3757`) and `craftDurationTicks` (`:3768`). **`RefineRecipeDef` carries NO tier** (`model.ts:3118-3122`), and `ITEMS[].tier` is the WAREHOUSE tier (all current items are T1), so it cannot stand in. The XP weight model therefore needs a new data field on refine recipes; see section 6.
- Live data for worked examples: `refineCommonOre` 20 ore -> 1 ingot, 12 ticks; `refinePolysilicateWafer` 5 -> 1, 20 ticks (`model.ts:3151-3162`). Blueprint craft durations are "tier-1 ~120 ticks, tier-2 ~300". Ship `buildRecipe.durationTicks` ranges 300 (corvette) to 1200 (`model.ts:787-898`).

**Salvage (the exclusion is deliberate and guarded):**

- `salvage.ts:21-32` states the parity boundary in the file header: three live only instant actions (`salvageEquipment`, `salvageSalvagedMaterial`, `salvageShip`), all using `Math.random` (injectable only for tests), all forbidden from the tick path.
- `salvage.test.ts:290-301` enforces it by loading `./tick.ts?raw` and asserting the source does not contain `salvageEquipment`, `salvageSalvagedMaterial`, `salvageShip`, or `./salvage`. **This guard breaks the moment salvage is queued** and must be rewritten, not deleted (section 7).
- `salvageShip`'s own header (`salvage.ts:437-444`) already anticipates this exact conversion: "a FUTURE task converts it into a MULTI-TICK TIMED teardown process ... at which point it moves into the tick path and takes on its OWN offline-parity obligation."

**Talents:**

- `HomeworldTalentEffect` (`model.ts:5577`) is a 5 member union including `unlockCaptainSlot` and a `none` placeholder; `HomeworldTalentDef` supports an optional `requiresFleetAdminLevel` wall.
- `fleetLogisticsSlot1/2/3` (`model.ts:5915-5947`) is the exact chain to mirror: three adjacency linked nodes, each `{ type: "unlockCaptainSlot" }`, each with its own `cost` and FA level wall.
- `MAX_UNLOCKABLE_CAPTAINS` (`model.ts:6080`) is **derived by counting nodes**, not hardcoded, so the ceiling grows when a node is added. The queue depth helper copies this pattern exactly.
- `industryBonusOutput` (`model.ts:~6050-6062`) currently carries an honest but **inert** `{ type: "none" }` after the legacy `recipeBonusOutput` retirement. It is the natural home for the new iLevel talent (section 6.4).

**UI:**

## 5. The queue engine

### 5.1 Data model

One new top level array, mirroring `activeProcesses`:

```ts
// model.ts
export type QueueFacilityKey = "refinery" | "fabricator" | "salvageBay";  // extensible union

export type QueuedOrder =
  | { type: "craftLine"; kind: CraftLineKind; recipeKey: string; mode: CraftLineMode }
  | { type: "salvage"; target: SalvageTargetRef };

export interface QueuedJob {
  id: string;                 // "q-N", minted from state.nextQueueId (mirrors nextProcessId)
  facility: QueueFacilityKey;
  order: QueuedOrder;
}

// GameState gains:
//   processQueue: QueuedJob[];   // FIFO by array index; the index IS the queue order
//   nextQueueId: number;
```

**Why one flat array rather than a per facility array:** it mirrors `activeProcesses` exactly (one field, one migration, one resolver pass, one save shape), and per facility DEPTH is then enforced by counting entries whose `facility` matches, derived on read, never stored. A per facility array shape would fix the facility set in the schema, so adding the research queue in 0.13.4 would need another migration; the flat array plus a widened union needs none.

**Why the queued unit is an ORDER, not a job:** for refine/fabricate the player's unit of intent is a **line** (recipe + batch count or continuous), not a single iteration. Queuing lines means "when a slot frees, configure it with this next", which is the actual mental model, and it lets promotion delegate straight to the proven `canStartLine` / `startLine` pair instead of duplicating the per iteration engine. ~~For salvage the unit is genuinely one target, which the same union expresses.~~

### 5.2 Talent gated depth

**Recommendation: depth is PER FACILITY, granted by ONE shared talent chain.**

Each learned node grants `+1` queued slot **to every queue capable facility**, and each facility's queue is counted separately against that depth.

Reasoning:

- A **shared pool** (one global depth spent across facilities) creates silent cross facility starvation: queue five refine orders and your fabricator queue is full, with no console able to explain why. That is a surprise, and surprises are a peace violation.
- **Per facility** capacity is what a console can honestly display next to its slots ("Lines 2 / 3 | Queued 1 / 2"), self contained and legible.
- Keeping **one talent chain** (rather than one per facility) preserves the "RAM is expensive" fiction: you upgrade the machine, and the whole machine gets deeper buffers. It also avoids a combinatorial talent web.
- **Tradeoff, stated:** one node therefore multiplies total queued capacity by the number of queue capable facilities. Accepted, because a queued order is not free (it competes for materials at promotion time and it occupies visible UI), and because generosity here is the point of the feature.

**Recommendation: the ACTIVE job does NOT consume a queue slot.** Depth counts only not yet started orders; running work is governed by the facility's existing SLOT count.

Reasoning: slots and queue depth are two already legible, orthogonal resources. Making the active job eat a queue slot means a depth-1 player can queue nothing at all, which reads as a broken feature, and it couples the facility upgrade track to the talent track for no design gain. The honest readout is "3 lines running, 1 waiting behind them".

**Recommendation: BASE depth 1 for every queue capable facility**, with talent nodes adding `+1` each.

Reasoning: a feature that ships at depth 0 for every new player is a feature nobody discovers, and the talent that unlocks it is then a talent nobody knows to want. One free queued slot is the taste; the chain is the investment. Proposed chain (mirroring `fleetLogisticsSlot1/2/3` shape and costs):

| Node | Effect | Gate |
|---|---|---|
| `fleetLogisticsQueue1` | `{ type: "queueDepth", depth: 1 }` | adjacency + adminPoints cost |
| `fleetLogisticsQueue2` | `{ type: "queueDepth", depth: 1 }` | + `requiresFleetAdminLevel` |
| `fleetLogisticsQueue3` | `{ type: "queueDepth", depth: 1 }` | + higher `requiresFleetAdminLevel` |

New `HomeworldTalentEffect` member `{ type: "queueDepth"; depth: number }`, and a **derive on read** helper that sums learned nodes exactly the way `salvageTalentBonus` (`salvage.ts:71`) sums `salvageBoost`:

```ts
export const QUEUE_DEPTH_BASE = 1;
export function queueDepth(state: GameState): number {
  return QUEUE_DEPTH_BASE + state.unlockedHomeworldTalents.reduce(
    (n, key) => n + (HOMEWORLD_TALENTS[key].effect.type === "queueDepth" ? effect.depth : 0), 0);
}
```

Summing (rather than short circuiting on the first) is what makes a fourth node land with zero engine change, the same forward property `MAX_UNLOCKABLE_CAPTAINS` (`model.ts:6080`) gets from counting nodes instead of hardcoding 4.

### 5.3 Reservation semantics for queued orders

**Recommendation: a QUEUED order reserves NOTHING. It is gated at promotion time by the existing `canStartLine`.**

Reasoning:

1. `allocatedItem` (`allocation.ts:128`) keeps reading **only active lines**. `allocation.ts` needs zero changes, `free >= 0` is preserved by construction, and there is no second reservation basis that can drift from the first. This is the derived-not-stored guarantee the whole subsystem was built around, and the cheapest way to keep it is to not touch it (Omega 15a).
2. Reserving at queue time is exactly the "safe, but locks resources" landmine SUGGESTIONS flags. A player who queues four orders would see `Free` collapse for work that will not run for hours, and the configurator's **Free / Allocated / Total** preview (preservation inventory 1b) would stop meaning what it says today.
3. Precedent already exists in the engine: a **continuous** line holds `remaining` at exactly 1, reserving only its single next iteration and nothing beyond it (`allocation.ts:64-66`). "Queued work reserves at most the next step" is the established stance.

**Tradeoff, stated plainly:** a queued order can find itself unaffordable when its turn arrives. That is handled below and surfaced, never silent.

### 5.4 Pause and resume on unaffordability

**Recommendation: strict FIFO array order, with SKIP-ON-BLOCK promotion.**

Each tick, per facility, while a slot is free: scan `processQueue` in array order for the first entry of that facility whose adapter `canStart` returns ok, and promote it. If the head entry is blocked, the scan continues to the next entry of that facility. **The array is never reordered.** A skipped entry keeps its position and is retried first next tick.

Reasoning: strict head-of-line blocking (refuse to look past a blocked head) is more predictable on paper, but it produces the worst possible offline outcome: you return after eight hours to find one unaffordable order at the head and every slot idle the whole time. That is precisely the friction this release exists to remove. Skip-on-block fills a slot whenever ANY queued order can run, never silently reorders the player's queue, and is still a pure deterministic function of state at that tick (so it stays closed form).

**Blocked state is DERIVED, never stored.** A queued row renders its live `canStartLine` reason through the existing `startLineBlockText` seam ("Waiting: not enough Titanium Ingot"). No `pausedReason` field, so it cannot go stale, matching `stepCraftLine`'s deliberate choice to drop the retired order's `pausedReason` bookkeeping.

**Continuous mode interaction (worth calling out at design time):** a continuous line never releases its slot, so anything queued behind it on that facility waits for a DIFFERENT slot to free, potentially forever. The configurator must say so on the continuous option ("runs until cancelled; queued orders wait for another slot"). Not a bug, but it is a trap if unlabeled.

### 5.5 Offline resolution: closed form, order preserving

The hard invariant is unchanged: `resolveProcesses(state, N)` must equal N applications of `resolveProcesses(_, 1)`, and completion order plus RNG draw order must be identical live versus one big offline span.

**The queue promotion pass MUST live in `economyTick`'s tail, beside `processRefineLines` / `processFabricateLines`, and never in a UI handler.** Concretely, a new exported `processQueue(state): GameState` runs in `economyTick` **after** `resolveProcesses` and **before** `processRefineLines` (so an order promoted into a line this tick is stepped by the line engine the same tick, exactly as a slot freed by a completion is refilled the same tick today).

This is closed form **by construction**, not by argument: `tick()` (`tick.ts:2966-2971`) steps offline as `economyTick(next, 1, rng)` per whole tick, and the live poll calls `economyTick(state, 1)` per whole tick, so the pass runs exactly once per tick on both paths. The bounded trailing fractional artifact documented at `tick.ts:2979-2996` applies to the new pass identically to the four existing passes: at most one extra promotion per offline catch-up, self correcting on the next whole tick. No new class of divergence.

**Ordering rules that must hold and must be tested:**

- `processQueue` iterates facilities in a **fixed declared order** (the `QueueFacilityKey` union order), not `Object.keys` over a runtime map, so promotion order is deterministic.
- Within a facility, the queue is scanned in array index order.
- Promotion **does not draw RNG**. Every queued promotion is a `startProcess` (deduct at start), and every RNG draw still happens at COMPLETION inside `resolveProcesses`. So the queue cannot perturb the RNG stream order; the only thing that changes stream order is the salvage work in section 7, which is tested separately.

**Required new parity tests** (on top of the existing 101, which must not change):

1. `economyTick` stepped 1 tick x N with a loaded queue produces a deep equal state to the same start advanced by `tick(N seconds, ...)`.
2. A queue that drains across a long offline span promotes the same orders in the same sequence as the live stepping did.
3. A queue whose head is unaffordable at tick k and affordable at tick k+m promotes at exactly k+m on both paths.

### 5.6 Per facility divergence: the adapter table

Only refine and fabricate share the line engine. Everything else starts its own way into one flat `activeProcesses`. The universal engine absorbs that with a **compile checked adapter table**, the same trick `PROCESS_XP_AWARDS` uses to make a new kind a compile error:

```ts
type QueueAdapter = {
  canStart(state: GameState, order: QueuedOrder): { ok: true } | { ok: false; reason: string };
  start(state: GameState, order: QueuedOrder): { next: GameState; started: boolean };
  hasFreeSlot(state: GameState): boolean;
};
const QUEUE_ADAPTERS: Record<QueueFacilityKey, QueueAdapter> = { ... };
```

- `refinery` / `fabricator` adapters delegate wholesale to `canStartLine` + `startLine` (`tick.ts:5811` and below). Zero new gate logic, so the queue can never diverge from what the configurator's Start button says.
- `salvageBay` adapter delegates to the new `canStartSalvage` / `startSalvageJob` (section 7).
- Adding `research` / `shipyard` / `fuelStorage` later means adding a union member and one row. Missing the row is a compile error.

`hasFreeSlot` is where the divergence actually lives: refine reads `refineSlotCount` versus `refineLines.length`, fabricate reads `fabricateSlotCount`, salvage reads its own new slot count. The promotion pass itself knows nothing about facilities.

## 6. Crafting level and iLevel redesign

### 6.1 The XP weight model

Today: `award = CRAFTING_XP_PER_DURATION_TICK (2) * durationTicks`, identical per tick for every kind. New:

```
award = floor( durationTicks * CRAFTING_XP_PER_DURATION_TICK * weightNum / CRAFTING_XP_WEIGHT_DENOM )
CRAFTING_XP_WEIGHT_DENOM = 4
```

**Integer arithmetic on purpose.** `durationTicks`, the base rate and `weightNum` are all integers, so the single division and floor at the end is exact and deterministic. This preserves the "integer x integer, no float drift" property the current constant's comment explicitly calls load bearing for closed form parity (`model.ts:5418-5420`).

Proposed weights (`weightNum`, i.e. quarters):

| Job | weightNum | Effective multiplier | Reasoning |
|---|---|---|---|
| `refineJob` | 1 | 0.25x | High volume, low value, no research gate, infinitely repeatable from mission loot. This is the bulk source the user named. |
| `fabricateJob`, MATERIAL blueprint | 4 x tier | 1.0x per tier | The current baseline, preserved for tier 1 so existing pacing is the anchor. Tier scaling is the "value" axis. |
| `fabricateJob`, EQUIPMENT or WEAPON blueprint | 6 x tier | 1.5x per tier | This is the output crafting level actually feeds (iLevel), so it should be the best way to raise it. |
| `shipBuild` | 12 | 3.0x | The largest, rarest, most component hungry build in the game. |
| everything else | 0 | none | Unchanged (`facilityUpgrade`, `researchProject`, `fuelRefineJob`, `equipmentStorageUpgrade`, `docksExpansion`, `shipRepair`, and the new salvage kind: see section 7). |

**Where the weight is read from.** Blueprints already carry `tier`, so equipment versus material is `blueprintMintsEquipmentInstance(bp)` and the tier is `bp.tier`: no data change. **Refine recipes carry no tier** (`model.ts:3118-3122`), so add one optional field:

```ts
export interface RefineRecipeDef {
  ...
  xpWeightNum?: number;  // defaults to REFINE_XP_WEIGHT_NUM (1) when absent
}
```

Recommendation: add the field but leave both current recipes on the default. Reasoning: it puts the tuning knob in the data table (where a future tier-2 refine recipe declares its own value) without pretending today's two recipes are differentiated. The alternative, deriving weight from the output item's `ITEMS[].tier`, is wrong: that field is the WAREHOUSE tier and every current item is T1.

**One property worth stating because it is easy to get wrong:** because the award is proportional to `durationTicks`, a facility SPEED multiplier (`refineSpeedMult`, `FACILITIES.refinery` rung 3) does not change XP per unit time. It delivers the same XP as more, shorter jobs. That is correct and desirable: speed upgrades should raise throughput, not XP rate. Verify at build time that the speed multiplier is applied to `durationTicks` at start (it is, in the line engine's duration derivation) and not to the award.

| `refineCommonOre` (20 ore -> 1 ingot) | 12 | 24 | **6** | 0.5 |
| `refinePolysilicateWafer` | 20 | 40 | **10** | 0.5 |
| Tier-1 material blueprint | 120 | 240 | **240** | 2.0 |
| Tier-2 material blueprint | 300 | 600 | **1,200** | 4.0 |
| Tier-1 equipment blueprint | 120 | 240 | **360** | 3.0 |
| Tier-2 equipment blueprint | 300 | 600 | **1,800** | 6.0 |
| Corvette hull | 300 | 600 | **1,800** | 6.0 |
| Largest hull | 1,200 | 2,400 | **7,200** | 6.0 |

### 6.3 The curve: gentle, then steep

```
craftingXpForNext(L) = CRAFT_XP_BASE * L^2 * (1 + L / CRAFT_XP_KNEE)
CRAFT_XP_BASE = 120        CRAFT_XP_KNEE = 20
```

A quadratic with a linear multiplier is a cubic in disguise: it behaves like the current quadratic early (where `L / KNEE` is small) and turns hard past the knee. Chosen over a raw exponential because an exponential's late levels become unreachable rather than expensive, and over a hand authored per level table because that is 50 numbers to maintain and re-tune.

| Level | Cost of this level | Cumulative to reach it | Cumulative under today's `500 L^2` |
|---|---|---|---|
| 2 | 126 | 126 | 500 |
| 5 | 3,750 | 4,200 | 15,000 |
| 10 | 18,000 | 46,350 | 142,500 |
| 25 | 168,750 | 1,128,000 | 2,450,000 |
| 40 | 576,000 | 6,115,200 | 10,270,000 |
| 50 | 1,050,000 | 13,854,750 | 20,212,500 |

The absolute scale drops because the weight model cut low value income hard (refining fell 4x). The **shape** steepens, which is the requirement: `forNext(40) / forNext(10)` is 32x on the new curve versus 16x on the old.

### 6.4 Proof: bulk refining cannot outpace meaningful crafting

Reaching **crafting level 40** (the tier-2 iLevel ceiling, see 6.5) costs **6,115,200 XP**. Two routes, using live data:

**Route A, pure bulk refining.** Refinery tops out at 3 slots (`FACILITIES.refinery` grants +1 slot at rungs 0/1/2, then a speed multiplier at rung 3). Each slot yields 0.5 XP per tick, so a fully upgraded Refinery earns **1.5 XP per tick**, and the rung-3 speed multiplier does not change that (6.1).

- Time: 6,115,200 / 1.5 = **4,076,800 ticks** at 1 second per tick (`tickDurationSeconds: 1`, `model.ts:6280`) = about **1,132 hours**, roughly 47 days of uninterrupted refining.
- Materials: 6,115,200 / 6 = 1,019,200 refine jobs x 20 `commonOre` = **20.4 million Titanium Ore**, against a base warehouse cap of 1,000,000 per item. The player must mine and consume 20 full warehouses of ore.

**Route B, tier-2 equipment fabrication.** Three fabricate slots at 6 XP per tick = **18 XP per tick**.

- Time: 6,115,200 / 18 = **339,733 ticks** = about **94 hours**.

Route B is **12x faster** and is the only route not gated on an absurd ore volume. Even the intermediate case (three slots on tier-1 material components, 6 XP per tick) matches Route B's rate while producing components the player actually needs. That is the user's constraint satisfied at the source: bulk refining still contributes (it is not zero, and it is not punished), it simply cannot lead.

Cross check at the low end, so early game is not punished: level 2 costs 126 XP, which is 21 refine jobs (about 84 seconds on one slot) or a single tier-1 component craft. Level 5 costs 4,200 cumulative, about 18 tier-1 component crafts. Gentle at first, as required.

### 6.5 iLevel mapping and the tier cap

`computeItemLevel` is unchanged in shape. The tier cap stays `blueprint.tier * EQUIPMENT_ILEVEL_CAP_PER_TIER (20)`, so with two content tiers the live ceiling is **iLevel 40**, reached at crafting level 40, and crafting levels past 40 do nothing until tier-3 content exists.

**Recommendation: keep the cap HARD.** The stated invariant in `itemgen.ts:65-73` ("a tier-1 recipe can never out-level tier-1 content") is a genuine content-integrity guarantee, and quietly breaking it to keep a talent relevant is the wrong trade. The curve is positioned so that hitting 40 is a real long game goal (about 94 hours of top tier fabrication), which means the cap is a destination rather than a wall players slam into on day two.

**`faTalentBonus`: WIRE IT.** New `HomeworldTalentEffect` member `{ type: "craftingItemLevel"; bonus: number }`, read at the three mint sites in `resolveProcesses` through a `craftingItemLevelBonus(state)` helper that sums learned nodes (same shape as `salvageTalentBonus`). Home it on the **industry** branch by re-wiring `industryBonusOutput` (`model.ts:~6050-6062`), which today carries an honest but inert `{ type: "none" }` placeholder left behind when `recipeBonusOutput` was retired. Suggested value `+2`.

Reasoning: it resolves a known dead node cheaply, it is thematically exact for an industry branch, and unlike the other candidate re-wire logged in SUGGESTIONS (a bonus-output CHANCE on fabricate) it needs **no RNG in the tick path at all**, so it carries zero offline parity risk. Its honest scope: it is a **catch-up** talent that gets you to the ceiling sooner and does nothing once you are at the ceiling. That is a real limitation and it must be described that way in the talent's flavor text rather than implied to be permanent power. See open question 2 for the alternative.

**`achievementBoost`: stays 0.** There is no achievement system. Keep the parameter, keep it at 0, and document it as reserved for the logged Player Score / achievements feature. Removing it would be churn for a hook we know is coming back.

**Grandfathering:** existing `craftingLevel` / `craftingXp` are untouched by the migration. No recompute, no rollback. Reasoning: silently demoting a player's crafting level because the designer retuned the weights is exactly the kind of surprise the peace rule forbids. Accepted consequence: existing saves keep a level that would now cost more to earn, which is a one time generosity, not an exploit.

## 7. Salvage as a queued process

### 7.1 What has to change

| Piece | Change |
|---|---|
| `TimedProcessKind` (`model.ts:2121`) | add `"salvageJob"` |
| `PROCESS_XP_AWARDS` (`tick.ts:691`) | **forced** new row (the Record is exhaustive) |
| `ProcessEffect` (`model.ts:2126+`) | add `{ type: "salvageResolve"; target: SalvageTargetRef }` |
| `resolveProcesses` (`tick.ts:6586`) | new completion branch calling the existing salvage functions **with the threaded seeded `rng`** |
| `salvage.ts` | unchanged math; the file header's parity boundary note is rewritten to describe the new one |
| `salvage.test.ts:290-301` | grep guard rewritten (7.5) |
| Salvage Bay | new slot count + queue, adapter row in `QUEUE_ADAPTERS` |

**`PROCESS_XP_AWARDS` row recommendation: `salvageJob: { fleetAdmin: false, crafting: false }`.**

Reasoning: salvage is recovery, not production. Granting crafting XP would create a closed loop, because `salvageEquipment` returns 30 to 40 percent of the recipe inputs (`SALVAGE_FRACTION_MIN/MAX`, `salvage.ts:96-97`): craft an item for 1,800 XP, salvage it for more XP, recover a third of the materials, repeat. That raises XP per material spent without producing anything, which is exactly the faucet `fuelRefineJob` and `shipRepair` are excluded to prevent. It joins those two as a neither-axis kind. Flagged as open question 1 because it sits slightly against "all crafting feeds crafting level".

### 7.2 Duration

Per the logged intent: the lowest tier salvage takes about **5 seconds** (5 ticks), scaling up with the target's quality, rarity and iLevel. Proposed first pass:

```
salvageDurationTicks = SALVAGE_BASE_TICKS(5) + iLevel * SALVAGE_TICKS_PER_ILEVEL(0.5)
                       + quality * SALVAGE_TICKS_PER_QUALITY(2), rounded up
```

Salvaged materials (the loot roll) use a flat `SALVAGE_MATERIAL_TICKS` (5). A ship teardown uses a share of `buildRecipe.durationTicks` (proposed one third), which finally delivers the timed teardown `salvage.ts:437-444` has been waiting for. All first pass tunables.

### 7.3 Consume at completion, reserve by derivation

Every other process deducts inputs at START. **Salvage deliberately deviates: it consumes AND rewards atomically at COMPLETION**, and the target is protected while queued or in flight by a derived reservation.

Recommendation and reasoning:

- Splitting `salvageEquipment` / `salvageSalvagedMaterial` / `salvageShip` into a consume half and a reward half would mean refactoring three proven functions, inventing a self contained snapshot payload for each (blueprint key, quality, hull BOM), and carrying that payload through save serialization. That is a large amount of surgery on working code (Omega 15a) for a property we can get another way.
- The **only reason** deduct-at-start exists is to close the double-spend window (`startProcess`'s header is explicit about this). A derived reservation set closes the same window with no refactor:

```ts
// derived, never stored: every instance id that a queued OR in-flight salvage owns
export function salvageReservedInstanceIds(state: GameState): Set<string>;
export function salvageReservedMaterialCount(state: GameState, itemId: string): number;
```

  built by scanning `processQueue` for `salvage` orders plus `activeProcesses` for `salvageJob` effects. This is the same derive-on-read discipline `allocatedItem` uses, and it cannot go stale.
- It is also **better UX**: the piece stays visible in the spare pool tagged "Salvaging, 12s" rather than vanishing for the duration. An item that disappears from your inventory for thirty seconds looks like a bug.

Consequences to enforce:

- `canFitEquipment` gains a `queuedForSalvage` reject reason, so a reserved instance cannot be installed out from under its job.
- A reserved instance cannot be queued twice.
- Salvaged material tiles show `Held: N (M queued)`, exactly the reservation aware stock idiom (preservation inventory 0.3), with `free = held - queued`.
- **Queueing salvage is NEVER blocked by `equipmentStorageCap`.** The escape valve guarantee (`salvage.ts:15-19`) says the storage cap is never consulted when recycling. A full spare pool must still be able to queue salvage, or a full pool becomes a softlock again. The in-flight piece continues to occupy its slot until completion; that is honest and does not break the guarantee.
- **Stale targets are a fail safe no-op.** A hull salvaged or lost while its job runs, an instance that has vanished, or a `lastShip` guard that now fires: the completion branch applies nothing, drops the process, and writes an event log line. Precedent: `clearShipDamage`'s documented "a stale shipId is a harmless no-op in the resolver" (`model.ts:2210`).

### 7.4 The RNG move

`salvageEquipment` and `salvageSalvagedMaterial` already take `rng` as an injectable third parameter defaulting to `Math.random`. The completion branch simply passes `resolveProcesses`' threaded seeded `rng` instead. Draw counts are already documented and fixed: `salvageEquipment` draws once (the recovery band), `salvageSalvagedMaterial` draws exactly twice (tier, then item), `salvageShip` draws once. That fixed, documented draw count is what makes the stream position predictable.

**Draw order rule:** salvage completions are resolved in `activeProcesses` array order like every other completion, interleaved with the existing quality rolls exactly as the array dictates. The existing quality roll parity test (`quality-roll.test.ts`) is the template for the new one.

### 7.5 Rewriting the grep guard

The current guard asserts a **proxy** (the string never appears in tick.ts) for the real invariant (**salvage never rolls on an unseeded stream inside the economy seam**). Once salvage is queued the proxy is false while the invariant must still hold. Delete nothing; replace it with guards on the real thing:

1. Every salvage call site in `tick.ts` passes the threaded rng: assert `/salvage(Equipment|SalvagedMaterial|Ship)\s*\([^)]*\brng\b/` matches, and that the count of matches equals the count of bare `salvage...(` occurrences.
2. `tick.ts` introduces no new `Math.random` (assert the existing occurrence count is unchanged, or that the salvage branch contains none).
3. `salvage.ts` still imports nothing from `tick.ts` (no cycle, direction preserved).
4. **The real proof:** a behavioral parity test. Identical seeded states, one advanced N ticks one at a time, one advanced by `tick(N, ...)`, both with salvage jobs completing mid span, must produce deep equal inventories including quality buckets.

The rewritten guard must carry a comment explaining what invariant it now defends, because a guard whose purpose is not written down gets deleted by the next person who breaks it.

### 7.6 Auto-salvage rules

**These live in `GameState`, not localStorage.** They change what the tick does, and offline resolution reads only the save. `salvageConfirmQualities` stays in localStorage because it only gates a live confirmation dialog and never affects state.

```ts
// GameState
autoSalvage: {
  enabled: boolean;              // default false
  maxQuality: number | null;     // auto-queue spares at or below this quality; null = off
  duplicates: boolean;           // auto-queue duplicates beyond keepPerVariety
  keepPerVariety: number;        // default 1
}
```

Rules:

- **Opt in, default off**, with every rule visible in the Salvage Bay and a plain language summary of what it will do ("Auto-queues spare systems at Q0 or below, keeping the best 1 of each type").
- Evaluated **in the tick path**, inside the same `processQueue` pass, so live and offline behave identically. It reads state only, draws no RNG, and is therefore closed form.
- **Bounded per tick:** it may add at most `depth - queued` orders per facility per tick, so it can never flood the queue or the loop (Omega 14: bounded work, no unbounded loop in the tick).
- **Deterministic candidate order:** candidates sorted by a stable key (instance id), never by iteration order over a map.
- **Never touches:** installed gear (`fittedToShipId !== null`), anything already reserved, and **Standard-Issue baselines**. Baselines DESTROY for zero reward (`salvage.ts:226-229`); auto-destroying items automatically is a data loss shape, so baselines are excluded from auto rules entirely and destroy stays a manual, deliberate act.
- **Respects the per quality confirm preference:** a quality tier whose `salvageConfirmQualities` checkbox is ON **cannot be auto-salvaged**. The player asked to be asked about that tier; an automation rule must not answer for them. This is the clean reconciliation between the two systems and it prevents the "it silently ate my Q4 drop" outcome.
- "Duplicates" is defined as same `slotType` + `varietyKey`, keeping the best `keepPerVariety` ranked by iLevel then quality then rarity.

## 11. Risks and watch items

1. **Parity is the top risk.** The suite must stay exactly 101 and the new queue and salvage parity tests are additions, not replacements. The specific hazards: a promotion pass that runs anywhere but `economyTick`'s tail; a salvage completion that draws RNG in a different order than the array dictates; any temptation to auto-start the next order from a UI handler "just for responsiveness".
2. **Reservation semantics.** The Free / Allocated / Total preview is the affordance most likely to quietly start lying. If anyone later argues for reserving at queue time, it must be a deliberate, tested decision with the preview relabeled, not a drive by change.
3. **The grep guard.** Relaxing a load bearing negative test is exactly how invariants die. The replacement must assert the real invariant and say so in a comment, and it must land in the SAME commit as the salvage move, never before it.
4. **Salvage as the deviation.** Consume-at-completion is the one place this design departs from deduct-at-start. It is safe only because the derived reservation set is complete: if any consumer of spare equipment is added later without consulting `salvageReservedInstanceIds`, double consumption becomes possible. Prefer to centralize the check behind the existing `canFitEquipment` seam rather than scattering it.
5. **Preservation loss in the UI pass.** Phase 6 touches six consoles. The Fuel Depot's four branch upgrade labeling, the configurator's Free/Allocated/Total preview, the Warehouse attention card and the Salvage-versus-Destroy label flip are the four that would be genuinely damaging to lose. Recommend a mechanical before / after diff of visible strings per console, the way the 0.13.1 and 0.13.2 regression audit was done.
6. **Balance.** Every number in section 6 is a first pass. The curve is positioned against a **two tier** content ceiling (iLevel 40); when tier 3 lands, `CRAFT_XP_BASE` and `CRAFT_XP_KNEE` must be revisited in the same pass, not after. Also note the queue itself raises effective XP income by removing idle gaps, so the weights should be re-checked once the queue is live rather than tuned only against pre-queue throughput.
7. **Scope and peel points.** Phases 5 (auto-salvage) and 6 (the UX pass) are the intended peels into 0.13.4; phase 4 (queue and salvage UI) is the second peel if needed. Phases 1 to 3 are the coherent minimum that still ships value.
8. **Terminology.** INSTALL / INSTALLATION for gear, never fit / fitment, in all new copy. Sweep the crafting consoles for stragglers while they are open.

## 13. Open questions for the user

1. **Should salvage grant crafting XP?** Recommendation is **no** on both axes (section 7.1), because salvage returns 30 to 40 percent of inputs and an XP award would make craft-then-salvage a net XP faucet. The counter argument is the locked "ALL crafting contributes" intent. Options: (a) zero, recommended; (b) crafting XP at a very low weight (say `weightNum` 1, matching refine) accepting a small loop; (c) crafting XP only for ship teardown, which cannot loop cheaply.
2. **Should the FA iLevel talent be able to exceed the tier cap?** Recommendation is **no** (keep `min(..., cap)` hard), which makes the talent a catch-up rather than an endgame power. Options: (a) hard cap, recommended; (b) the talent extends the cap by its bonus (`min(level + achievement, cap) + faTalentBonus`), which keeps it live forever but lets a tier-1 recipe out-level tier-1 content; (c) leave `faTalentBonus` at 0 this release and defer the whole question.
3. **Base queue depth: 1 or 0?** Recommendation is **1** for discoverability. Zero makes the talent chain feel more earned and is more faithful to "RAM is expensive", at the cost of shipping a feature most players never see.
4. **Auto-salvage duplicate definition.** Recommendation: same `slotType` + `varietyKey`, keep the best `keepPerVariety` (default 1) ranked iLevel, then quality, then rarity. Is "best" the right ranking, and should the default keep count be 1 or 2?
5. **Modal extraction.** SUGGESTIONS blocks standardizing the 0.13.2 modal until you have tested bottom-sheet-on-mobile. Has that call been made? If yes, 0.13.3 extracts the shared component (better) rather than mirroring the markup (safer but duplicative).
6. **Carry in the 0.13.2 navigation fix?** The regression audit found the captain page's Ship Systems shortcut no longer has a return path (`shipsReturnTo`). It is a Ships tab item by the series rule but it is small, unowned, and currently live. Include here, or leave for a tidy-up patch?
7. **Queue promotion: skip-on-block or strict head-of-line?** Recommendation is **skip-on-block** (section 5.4), so a single unaffordable order cannot idle a facility for an entire offline span. Strict FIFO is more predictable to explain; skip-on-block is far kinder to an offline player.
8. **How visible should crafting XP be?** Recommendation is a per recipe XP award on the Fabricator and Refinery rows plus a crafting level panel showing "your crafts currently roll at iLevel N (ceiling M)". A weight system the player cannot see cannot be reasoned about, but it is also new UI surface in an already large release.

## 15. LOCKED (user sign-off 2026-09-04): LANES and QUEUE DEPTH are two independent axes

**Status: LOCKED. This section OVERRIDES any narrower reading of sections 2, 5.2, 8.6, 8.7 and 8.8.** It is the authoritative statement of the throughput model for the whole Facilities tab. If a future doc, plan, task list or code comment disagrees with this section, this section wins and the other artifact is the thing that needs fixing.

Read this section before planning, estimating or building anything that touches facility throughput.

### 15a. The pattern, stated plainly

There are **two separate progression axes** on a production facility. They are bought with different currencies, they answer different questions, and **they never multiply into each other**.

| Axis | Question it answers | Bought with | Where it lives in code |
|---|---|---|---|
| **LANES** | How many jobs does this facility run **at the same time**? | **Facility upgrades** (credits + materials + facility level) | Per facility derived helpers in `tick.ts`, summed off reached upgrade rungs |
| **QUEUE DEPTH** | How far **ahead** may the player plan **at this facility**? | **Homeworld talents** (`fleetLogisticsQueue1/2/3`, adminPoints) | `queueDepth(state)` in `tick.ts:586`, base `QUEUE_DEPTH_BASE = 1` (`tick.ts:557`) |

The four rules, in the order they are most often got wrong:

1. **QUEUE DEPTH IS PER FACILITY. IT IS NEVER PER LANE.** One number applies independently to each queue capable facility. It is not divided between facilities, and it is not multiplied by anything inside a facility.
2. **NO UPGRADE MAY EVER GRANT QUEUE DEPTH PER LANE.** The user's exact framing, recorded verbatim: *"There are no upgrades that give +1 queue slot X lane."* A rung, talent or effect whose payload means "plus one queued slot, per lane" is forbidden. Not deferred, not a tuning question. Forbidden.
3. **THE ACTIVE JOB DOES NOT CONSUME A QUEUE SLOT.** Depth counts NOT-YET-STARTED orders only. Work already running is governed by the lane count. The honest console readout is "3 lines running, 1 waiting behind them".
4. **LANES ARE BOUGHT WITH FACILITY UPGRADES, DEPTH IS BOUGHT WITH TALENTS.** The two currencies stay separate on purpose, so neither track can be short circuited by grinding the other.

**Why the axes are kept separate (user rationale, recorded so it is not re-litigated as an efficiency question):** it stretches the content out by giving the player more to upgrade, in a way that provides a real benefit rather than being extension for its own sake. It is also **reversible later** if it turns out to be a nuisance in play, which is precisely why it is safe to lock now.

### 15b. Worked example: the case most likely to be got wrong

A player has bought a facility all the way to **10 lanes**, and has learned **exactly one** queue depth talent (`fleetLogisticsQueue1`, `+1`).

```
lanes at this facility        = 10          (from facility upgrade rungs)
queueDepth(state)             = QUEUE_DEPTH_BASE (1) + 1 talent rung (1)
                              = 2
queued slots at this facility = 2           <-- CORRECT
```

**The answer is 2.**

- It is **not 11** (lanes plus one). Lanes are not queue slots and are never added to them.
- It is **not 20** (depth times lanes). Depth is never multiplied by the lane count.
- It is **not 1 shared across the whole game.** The same player also has **2** queued slots at every other queue capable facility, independently.

What that player can do at that facility right now: run **10 jobs concurrently**, with **2 further orders waiting** behind them. Total work lined up = 12 things, of which 10 are moving and 2 are parked. Add a second queue talent and it becomes 10 moving, 3 parked. Add a lane upgrade instead and it becomes 11 moving, 2 parked.

### 15d. Checklist: how to add a facility to this pattern

Everything below is enforced by **exhaustive `Record`s over a union**, which is the point: adding a facility to `QueueFacilityKey` **without** completing this list is a **COMPILE ERROR**, not a silent runtime gap. Do not weaken any of these types into partial or index-signature records to "get it building".

**Adding a QUEUE to a facility:**

1. **Widen the union.** Add the key to `QueueFacilityKey` (`model.ts:3035`). This one edit deliberately breaks the build until every step below is done.
2. **Add the adapter row.** `QUEUE_ADAPTERS` (`tick.ts:7245`) is `Record<QueueFacilityKey, QueueAdapter>`, so the missing row fails `npm run check`. Supply `hasFreeSlot` / `canStart` / `start`. **Keep every member a one line delegation** to the function that already owns that question. Zero gate logic lives in the table, so the queue can never form a second opinion about whether a job may run.
3. **Add it to the promotion order.** `QUEUE_FACILITY_ORDER` (`tick.ts:7271`) is a literal tuple, never derived from `Object.keys`, because promotion order is a stated engine property that decides which facility wins a contested material in a tick. Its companion type alias `UnlistedQueueFacility` proves the tuple is complete: leave the key out and `npm run check` fails on the second half too.
4. **Add its `slotsTotalFor` arm.** `craftQueue.ts:432` maps the facility to its LANE count. Return the facility's derived lane helper. Return `SALVAGE_SLOT_COUNT`-style flat constants only where there genuinely is no level track.
5. **Add its `ENQUEUE_PROBE` row.** `craftQueue.ts:484` is another exhaustive `Record<QueueFacilityKey, QueuedOrder>`, same discipline.
6. **Do NOT touch `queueDepth`.** `queueDepth(state)` (`tick.ts:586`) is facility agnostic by design: it returns ONE number that applies to each facility independently. A new facility needs **no** change there, and **must not** acquire a per facility or per lane depth override. If you find yourself editing `queueDepth` to add a facility, stop: you are about to break rule 15a.2.
7. **Enforce depth by counting matches, never array length.** `state.processQueue` is one flat array. Per facility depth is enforced by counting entries whose `facility` matches (`queuedForFacility`, gate at `tick.ts:7413`), derived on read, never stored.
8. **Tests.** `craftQueue.test.ts` keeps a runtime `QUEUE_FACILITIES` list that is asserted equal to `QUEUE_FACILITY_ORDER` and to `Object.keys(QUEUE_ADAPTERS)`, so the new key must be added there too. Parity cases are additions, never replacements.

**Adding LANES to a facility:**

1. Give the facility a **level track** with upgrade rungs, if it does not have one (this is the Salvage Bay's actual blocker, not the lane helper itself).
2. Add an **additive effect member** to the facility upgrade effect union (`model.ts`), following `addRefineSlots` / `addResearchSlots` / `addFabricateSlots` / `addFuelPipelines`.
3. Add a **derived helper** in `tick.ts` that SUMS that effect over **reached** rungs only, copying `refineSlotCount` line for line. Derive on read, never store: a stored count goes stale, a derived one cannot.
4. **The effect payload must mean "plus N concurrent jobs at this facility". It must never mean, imply, or be reused to mean queue depth.** See rule 15a.2.

### 15e. Why this got lost the first time, and the rule that prevents it

**What happened.** The user stated a broad scope for queues. The design doc encoded a **narrower** one (section 2 shipped queue UI on three facilities, with the rest listed as deferred). The build then followed the doc faithfully for dozens of commits. Nobody noticed the gap until the user saw queues on 3 facilities instead of all of them. Every individual commit was correct against its instructions. The instructions were the thing that was wrong, and being faithful to them is exactly what made the divergence invisible for so long.

**Why a thin doc is dangerous rather than merely incomplete.** Once a decision is written down, it stops being questioned. The doc becomes the ground truth for every downstream plan, task list and review, and the user's actual words stop being consulted. A narrowing that survives into the doc is therefore not caught by more careful implementation, more review, or better tests. All of those check the work against the doc.

**The rule, and it is the whole point of this section being LOCKED:**

> **Reconcile a plan against the USER'S OWN STATED SCOPE, not merely against the design doc, before building.**

In practice, before any build phase starts:

1. Go back to what the **user actually said**, in their own words, not the doc's paraphrase of it.
2. Diff that against the doc's scope section, **item by item**. A doc that lists fewer things than the user asked for is a **narrowing**, and a narrowing is a **defect** until the user has explicitly approved it as a deferral.
3. Any narrowing that survives must be **visibly marked as deferred, with a reason and a named target release**, so it reads as a decision rather than as an omission.
4. This is the [[feedback_verify_notes_before_build]] rule, and it now has a second confirmed instance. Treat it as load bearing.

**Corollary for this section specifically:** section 15c's exclusion list is deliberately worded as PERMANENT rather than deferred, precisely so that the next reader cannot mistake an omission for a pending item. That is the shape every future scope boundary in this series should copy.
