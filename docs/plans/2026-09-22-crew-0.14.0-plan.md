## Crew design — consolidated spec (LOCKED with the user 2026-09-22/23)

Everything in this section is user-decided; magnitudes and per-hull numbers marked "tuning" get first-pass
values in Phase 0.5.

### Races (roster LOCKED)
Model = human origins + allied species. Each origin AND species is its own `race` entry in the signature
(~10 races). Gender is inclusive (male/female/nonbinary), purely cosmetic, no mechanical effect.
- **Human origins (6):** Earth-born (balanced), Martian (engineering/efficiency), Belter (flight-deck/EVA),
  Outer-Colony (security/survey), Station-born (operations/logistics), Spacer (endurance/long-haul).
- **Allied species (4, working names, distinct from the hostile aliens / First Cause):** Vael
  (science/sensors), Ossir (security/boarding-defense), Stheni (engineering/repair), Draell
  (flight/fuel-efficiency). Lore note: these are NEW canon (lore has aliens only as antagonists).
- **Racial bonus is CONTEXT-SCALED:** each race's trait carries two magnitudes, STRONG as a Senior Staff
  officer's racial, TINY per-head in the Complement rollup. `CREW_RACES` stores per-context magnitudes.

### Professions -> primary buff pools (Proposal A, LOCKED)
Each profession's buff is its main effect; each has a POOL of a few variants (roll picks from the pool).
Every profession earns its keep in today's missions/patrols; some deepen with Exploration/away-teams.
- **Operations:** faster homeworld unload · faster pre-mission load · larger effective cargo.
- **Flight-Deck:** faster transit-out · faster transit-back · smoother drone handling.
- **Engineering:** engine efficiency (range) · hull repair rate · power efficiency.
- **Security:** boarding defense · internal counter-infiltration · away-team protection. Deliberately
  ONBOARD + away-team protection, NOT ship-weapon buffs (those stay on combat gear, so crew never double-dip).
- **Science:** extraction yield · rare-find chance · survey aptitude (survey/sensors deepen in Exploration).
- **Medical:** crew-effectiveness multiplier · reduced crew losses · triage (away-team triage in Exploration).

### Buff count + magnitude model (LOCKED)
- **Buff COUNT is gated by RANK, not rarity.** Low ranks carry 1 buff; higher ranks carry more (first-pass
  in the rank table below). The extra buff is either a 2nd from the crew's own profession pool OR one from a
  **second-level-exclusive pool** (proposed global: ship-wide crew-output multiplier · craft duplicate-chance
  · across-the-board mission-turnaround cut · prevent-a-crew-loss chance).
- **Rarity is a MULTIPLICATIVE magnitude modifier** on the buff (small, e.g. stellar ~x1.35 on a 0.20% buff
  -> 0.27%, NEVER additive to 5.20%). Decoupled from rank.
- **Crew rarity is CAPPED AT STELLAR** (build the full derelict->constellar wiring, but the crew generator
  stops at stellar). First-pass multipliers: derelict x0.9 · standard x1.0 · augmented x1.15 · stellar x1.35.
- **Rank also scales magnitude** modestly; promotions (Senior Staff) add buffs.

### Rank ladder + command structure (LOCKED)
- **Complement ladder (8 tiers):** enlisted Crewman -> Petty Officer -> Chief -> Master Chief; then the
  officer track Cadet (a Master Chief who enrolls: enlisted -> officer trainee) -> Ensign (commission) ->
  Lieutenant -> Lieutenant Commander. **Commander is reserved for Senior Staff** (crowns the continuum).
- **Buff count by rank (first-pass):** Crewman 1 · Petty Officer 1 · Chief 2 · Master Chief 2 · Cadet 2 ·
  Ensign 2 · Lieutenant 3 · Lt Commander 3 (+ eligible for the exclusive pool). Tuning.
- **Command structure is a PER-HULL-TYPE template** (role dictates the mix: a destroyer weights Security/
  Engineering/Flight, a medical/support hull weights Medical/Science, a prospector weights Operations, an
  explorer weights Science/Engineering/Medical). Each hull's template = total complement cap -> per-division
  caps -> per-rank caps, all ABSOLUTE counts. Tuning.
- **Rank caps are INCLUSIVE/CASCADING from the top:** the cap at a rank counts everyone at that rank OR
  HIGHER, so unused high-rank capacity rolls down (1 LtC + 2 Lt + 4 Ensign, with no LtC/Lt crew, allows up to
  7 Ensigns). The lowest rank is bounded only by the division total.
- **Total cap ties to the `quarters` module:** base from the hull's crew capacity (reserved `crewStations`
  stat), raised by the crew-quarters module.

### Assignment (LOCKED)
- **Passive (default):** auto-fills each hull's template TOP-RANK-DOWN from the available pool (LtC slots
  first, cascading to Cadet, backfilling the remainder), silently, up to 100%. A random-but-sensible,
  role-appropriate crew with zero micromanagement.
- **Active:** the player assigns SPECIFIC crew to a SPECIFIC ship; the assignment holds whether the ship is
  docked (crew wait on the homeworld) or deployed. Same for Senior Staff (officers assigned to a ship, parked
  or not).

### Senior Staff (LOCKED, refines C.1)
Few named officers in bridge SEATS (the 7 in enum A). They provide LARGER, SWEEPING, UNIQUE bonuses (a bigger
class than the complement's small pools), scale by officer rank + promotions (Ensign -> ... -> Commander), and
carry a strong-magnitude racial. No rarity tier (rarity is complement-only). Hourly-refresh candidate roster;
fireable; promotions add/strengthen bonuses.

### Progression (LOCKED, solves the "1,000-crew tedium")
- **Complement:** rank + rarity LOCK at generation. You never promote individuals; you improve a ship's
  complement by ACQUIRING a better pool (transports + active curation) within the command-structure caps.
- **Senior Staff:** promoted individually (few of them), each promotion adding/strengthening bonuses.

### Phase 1 refinements + SEAT-MATCHING (user, 2026-09-23)
- **Seats are TYPED, not generic slots.** Each hull has ONE of each of the 7 seat TYPES
  (Executive/Pilot/Operations/Science/Tactical/Medical/Engineering). An officer is generated WITH a
  seat-type and can ONLY fill its matching seat (no stacking 7 Tacticals). A full bridge = finding/rolling a
  good officer of each of the 7 types; that IS the roster-cycling loop.
- **Senior Staff rank ladder = 5, starting at CADET:** Cadet -> Ensign -> Lieutenant -> Lt Commander ->
  Commander. Updates `OfficerRank` (Phase 0 had 4 starting Ensign). Lore: jump gates gone -> society
  reorganizing -> recruitment exploding -> green cadets crewing bridges is in-fiction.
- **Candidate roster: base 10, EXPANDABLE via an upgrade** (cycling for the right officer to eventually
  captain is a real loop).
- **Officer power keys off the stats that accentuate the hull you are flying** (officer<->ship synergy);
  the bridge module amplifies this (see tabled modules).

## Data model (the heart: why crew do NOT need full objects)

Confirmed with the user 2026-09-22. A crewmember's *mechanically relevant* identity is a finite
**signature**; two crew with the same signature contribute identically to every rollup, differing only in
name/gender (pure flavor). So the persisted unit is a **bucket histogram**, not a person.

### Complement = signature buckets + a small notable roster
```ts
// mechanically-distinct crew identity (NO name/gender: those are flavor)
type CrewProfession = "security" | "engineering" | "science" | "medical" | "operations" | "flightDeck";
type CrewRarity = EquipmentRarity;         // reuse the ladder; the crew GENERATOR caps at "stellar"
type CrewRace =                            // 6 human origins + 4 allied species (see the design section)
  | "earthBorn" | "martian" | "belter" | "outerColony" | "stationBorn" | "spacer"
  | "vael" | "ossir" | "stheni" | "draell";
type CrewRank = 1|2|3|4|5|6|7|8;           // Crewman..Master Chief (1-4), Cadet..Lt Commander (5-8)
type CrewBuffId = string;                  // a rolled buff from the crew's profession pool (or the exclusive pool)

interface CrewBucket {
  profession: CrewProfession;
  rarity: CrewRarity;     // magnitude MULTIPLIER, not rank; locked at generation
  rank: CrewRank;         // gates buff COUNT + command tier; locked at generation (no per-individual leveling)
  race: CrewRace;         // determines the racial bonus (tiny per-head for complement)
  buff1Id: CrewBuffId;            // the primary rolled buff (always present)
  buff2Id: CrewBuffId | null;     // a 2nd buff at higher ranks only (from the profession pool or the exclusive pool)
  count: number;          // how many identical crew sit in this bucket
}

interface ShipComplement {
  buckets: CrewBucket[];        // populated buckets only
  mode: "passive" | "active";   // per-ship (== per assigned captain) toggle
}

interface NotableCrewMember {   // a "standout" the player plucked out; a real, bounded object
  id: string; profession; rarity; rank; race; bonusId;
  name: string; gender: string; favorite?: boolean;   // graduated from a bucket (count -= 1)
}
```
- **Rollup** (the thing that feeds ship stats) = sum over buckets of `contribution(signature) * count`,
  grouped by the stat each profession/bonus targets. O(distinct buckets), not O(headcount).
- **The unassigned pool** is itself a `CrewBucket[]` on `GameState` (the gacha influx lands here).
- **Assignment** (auto or manual) moves counts between the pool and a ship's `buckets`. "Hand-pick 300
  high-rank crew" = decrement pool buckets, increment ship buckets. Player picks *compositions*, never 1017
  humans.
- **Names/faces** are generated lazily and deterministically (seed = bucket signature + index) only when a
  manifest view is opened. Never persisted.
- **Standouts** graduate into `notableCrew` (bounded list) with a persisted name; their bucket count drops
  by one. This is the only place a complement crewmember becomes a full object, and it is bounded by design.

So "1,017 crew" persists as maybe a few dozen `CrewBucket` rows + a handful of notables. Save weight and
tick cost scale with distinct buckets, not headcount.

### Senior Staff = few, named, full objects (fine to persist)
```ts
type SeniorStaffSeat = "executive" | "pilot" | "operations" | "science" | "tactical" | "medical" | "engineering";
type OfficerRank = "ensign" | "lieutenant" | "lieutenantCommander" | "commander"; // promotion ladder (names TBD)

interface OfficerBonus { id: string; magnitude: number; }   // one of two rolled bonuses; magnitude scales with rank
interface SeniorStaffOfficer {
  id: string; seat: SeniorStaffSeat;
  name: string; race: CrewRace; gender: string;
  rank: OfficerRank; bonuses: [OfficerBonus, OfficerBonus];
  missionsCompleted: number;         // + achievement counters that gate promotion
  assignedShipId: string | null;     // mirrors EquipmentInstance.fittedToShipId authority
}
```
- ~7 per ship, hand-curated. Flat `GameState.officers: SeniorStaffOfficer[]` keyed to a ship by
  `assignedShipId` + `seat` (mirrors the `equipment[]`/`fittedToShipId` precedent at `model.ts:1232`,
  `equipment.ts:226`), NOT a per-ship sub-record.
- **Candidate roster** = ephemeral, regenerated each refresh window; deterministic from the window index
  (see engine). Hiring copies a candidate into `officers`; firing removes.
- **Bridge module** (reserved `bridge` slot, `model.ts:1169`) becomes a real installable stat-bearing piece
  that scales officer effectiveness. See the "reserved slots" sub-decision below (minimal-first, cuttable).

## Engine seams (each maps to a verified anchor)

1. **Crew rollup -> ship stats.** Compute a per-ship crew modifier and apply it as an OVERLAY at the shared
   fold seam `tick.ts:3633-3634`, using the exact overlay technique already used for `engineEfficiency`
   at `tick.ts:3643-3649`. `shipDerivedStats` (`model.ts:2150`, return shape `model.ts:1938`) stays pure;
   the crew overlay layers on top so live and offline share one path. Senior Staff officer bonuses apply at
   the same seam (NOT the captain-talent reducers at `tick.ts:473-573`, which only touch yield/loot).
2. **Unload-scaling.** In `effectiveMissionDef` (`model.ts:2211-2218`), which currently passes `unloadTicks`
   through UNSCALED: scale it by `cargoCapacity / BASE_CARGO`, then apply the crew/operations unload bonus.
   Characterization tests first to pin current timings before the change (balance guard).
3. **Roster refresh (game-time, never wall-clock).** No `Date.now()` (forbidden for offline parity,
   `tick.ts:6173-6177`). Model "once per real hour" as a `gameTimeSeconds` window:
   `windowIndex = floor(gameTimeSeconds / OFFICER_REFRESH_SECONDS)`; the candidate roster is generated
   deterministically from `windowIndex` (a seeded pure function), so offline needs no catch-up loop and the
   roster is identical live vs offline.
4. **Transport influx (game-time accumulator).** Mirror `refreshSalvageIdleWatch` (`tick.ts:6228`, keyed on
   `state.gameTimeSeconds`): each tick, deliver one seeded crew batch per elapsed transport window since
   `lastTransportWindow`, then advance it. Offline catch-up naturally delivers the backlog into `crewPool`.
5. **Auto-crew (passive default).** On mission start / as ships come online, fill a ship's complement from
   the pool up to its caps with a seeded random assortment (peace-preserving default, zero micromanagement).

## Reserved-slot modules (both IN; user 2026-09-22 kept quarters and asked it to grow)
- `bridge` module: add `bridge` to `EQUIPMENT_SLOTS`/generation so it mints a real installable piece that
  scales Senior Staff effectiveness (an `officerEffectivenessMult`, and room for more officer-facing stats).
- `quarters` "crew quarters" module: add `quarters` to `EQUIPMENT_SLOTS`/generation. Its core job is to
  **grant additional complement capacity** (raising the per-ship complement cap via the reserved
  `crewStations` stat key, `model.ts:1625-1651`), and it is the natural home for other complement-facing
  options (e.g. per-type cap shaping, crew-comfort/efficiency via the reserved `crewEfficiency` key, morale
  or retention levers). Treated as a first-class craftable piece like the bridge module, not an add-on.
  Concrete stat list for the quarters module is a Phase-4 tuning item; the slot + the capacity role are core.

### Personnel Rosters: partial-fill + the capacity/linkage model (user datadump 2026-09-24, FORK OPEN)
- CONFIRMED: PARTIAL rosters auto-complete on USE. If a roster hand-fills only part of the complement (e.g. 128

  - (A) LINK TO ARMORY LOADOUT: the roster references an Armory loadout (ship + equipment), which yields the EXACT

    list, assigns down the list up to each rank's cap, and does not assign the overflow. Requires: reordering crew

    and who to move. More functionality, but portable across ships.

  (2) travel as a full "ship + gear + people" package. Keeps portability (a general roster works on any hull,
  capped by it) AND exactness (link for a locked package). REQUIREMENTS this locks in: the roster is a REORDERABLE
  ordered list; every entry shows its POSITION in the order so the player can see who to move up/down; assignment
  walks the list in priority order, filling each rank up to that ship's cap and spilling the overflow back to the
