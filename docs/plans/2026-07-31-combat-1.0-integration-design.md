# Combat 1.0 Integration Design (gear, stats, drones, modules)

> **For Claude:** This is the design for the Combat 1.0 integration epic, the sequel to `2026-07-22-combat-0.13.0-design.md`. 0.13.0 shipped the simulation ENGINE (honest, unit-tested, live in patrols) but fed it hardcoded placeholder inputs. This epic wires the engine to real, player-crafted gear and lights up the dormant systems. It is a LARGE multi-phase epic. This doc is the durable artifact; the phased implementation plan (`superpowers:writing-plans`) comes next, then subagent-driven build. Nothing here is built yet.
>
> **Status:** DRAFT for user review. Sections tagged `DECISION` are load-bearing forks that need explicit sign-off before the plan is written. Everything else is a recommendation open to correction.

**Goal:** Turn combat from a fixed-per-hull system into a gear-driven one. Weapons, shield emitters, hull plating, and drone pods become craftable, implicit-rolled items that flow through the existing 0.11.0 itemgen engine; every combat stat the sim already consumes gets wired to real ship/gear inputs instead of a hardcoded `0`; the seven dormant status effects are lit; modules add active abilities; and enemies gain a matching stat model so patrols stay winnable. When it is done, a ship with no weapon, hull plating, or shield installed cannot initiate combat, and crafting better gear is the whole point of fighting.

**Release shape (locked with user 2026-07-31):** All of "Tier A" from the completeness audit is in scope. The build is phased with a rebalance + parity gate per phase. Modules land last. Combat stays on devpreview for the entire epic and debuts to prod ONCE, fully complete. Because combat never shipped to prod, there is no live-combat save to migrate: the migration only carries a pre-combat (0.12.1-shaped) save forward and auto-installs the Standard-Issue combat baseline.

**Relationship to prior docs:** This extends, and does not contradict, `2026-07-22-combat-0.13.0-design.md` (the engine) and `2026-07-17-ship-equipment-combat-epic-design.md` (the original vocabulary: hardpoint counts, the disruption table, per-type resists, Battle Rating). Where those docs deferred an item to "Phase 9 / Phase 12 / later sub-phase," this epic is that phase. The 0.11.0 equipment engine (`itemgen.ts`, `EQUIPMENT_SLOTS` in `model.ts`, `EquipmentTooltip.svelte`) is the proven foundation we extend; it already does implicit + affix + variety + quality/rarity/iLevel rolls, and reusing it is the single biggest de-risker of this epic.

## 0. Governing principles (inherited + epic-specific)

Inherits all nine governing principles from the 0.13.0 design (determinism, offline == live HARD invariant, two RNG streams, integer/fixed-point math, bounded work, forward-wired hooks, single event stream, no em dashes). Epic-specific additions:

1. **Extend, do not reinvent.** Combat gear is a new set of `EquipmentSlotType`s flowing through the EXISTING itemgen budget engine. We do not build a parallel item system. If a combat slot needs a stat the engine cannot express, we add the stat key to the shared allow-set, not a new pipeline.
2. **Never-brick, but blockable.** Every combat hull always ships with a free Standard-Issue baseline in its required combat slots, so a fresh or migrated ship is always dispatchable. The baseline is stat-real but weak. The blocker (Section 3) fires ONLY when a player deliberately strips a required slot bare.
3. **Parity is a per-phase gate, not an end-of-epic prayer.** After every phase, the 100-test offline-vs-live parity fuzz must be green before the phase is considered done. Each new wired input is an outcome surface; landing them one phase at a time keeps a desync bisectable (audit flag #2).
4. **Balance is tuned per coherent slice.** Enemy waves + durability are retuned at the end of each phase against that phase's new inputs, played, then the next phase starts. We never tune a moving target (audit flag #1).
5. **The consumers already exist.** `resolveBattle.ts` already reads armor, dampening, evasion, resists, attenuation, and every disruption field. This epic almost never touches the sim's math; it feeds that math real numbers. The exception is modules (Section 10), which is genuinely new sim architecture.

## 1. The root refactor: fitted combat gear on the ship model

The entire audit collapses to one seam: the ship model has no fitted-combat-gear fields, so `shipToCombatant` (`bridge.ts:269`) reads `COMBAT_DEFAULT_LOADOUT[hullType]` and a wall of hardcoded `0`s instead of installed gear.

The fix, done once, unblocks almost everything:

- Combat gear is stored the same way economy equipment already is: as `EquipmentInstance` records in `state.equipment`, with `fittedToShipId` + a combat `slotType`. No new storage collection.
- `shipToCombatant` changes from "read the hull default" to "read the ship's fitted combat gear, fall back to the hull default only where the design still wants a hull-intrinsic value" (hull base integrity, for instance, may stay a hull property that armor gear ADDS to, rather than replaces; see Section 6 DECISION).
- `COMBAT_DEFAULT_LOADOUT` does not disappear. It becomes the definition of each hull's Standard-Issue baseline loadout (Section 3), the thing auto-installed on build and migration.

This section is the spine of Phase 1. Everything in Sections 2 through 8 rides on it.

---

## 2. Combat slot layout and hardpoints

New `EquipmentSlotType` members join the existing four (`cargoBay`, `ftlDrive`, `reactorCore`, `specUtility`):

- `weapon` (multi, up to the hull's hardpoint count)
- `shieldEmitter` (singleton)
- `hullPlating` (singleton)
- `module` (multi, up to the hull's module-slot count; Phase 3 only)
- `droneHangar` / drone-pod bays (Phase 2; see Section 9 for whether pods are a slot type or a nested structure)

**Hardpoint + slot counts per combat hull.** `DECISION 2a.` The epic doc (S1a) specified hardpoint counts for all ten hulls; only the three combat hulls matter for 1.0. The current hardcoded loadout uses fewer weapons than the epic's hardpoint counts (it left room "for fitment"). Recommended reconciliation, adopting the epic counts as the fit BUDGET and letting Standard-Issue fill only part of it:

| Hull | Weapon hardpoints | Shield | Hull plating | Module slots | Built-in drone bays |
|---|---|---|---|---|---|
| Destroyer | 4 | 1 | 1 | 1 | 0 |
| Battleship | 6 | 1 | 1 | 2 | 0 |
| Carrier | 2 | 1 | 1 | 1 | 2 (+ hangar-gear bays, Section 9) |

These are first-pass tunable, same spirit as every economy constant. The point of sign-off is the SHAPE (weapons scale with hull size; carrier trades guns for bays), not the exact integers.

## 3. Standard-Issue combat baseline + the dispatch blocker

This reconciles the two things the user asked for that sound contradictory: "free Standard-Issue set" AND "empty slots block combat."

- **Required combat slots** for a combat hull: at least one `weapon`, the `shieldEmitter`, and the `hullPlating`. (Modules and extra hardpoints are optional, never blockers.)
- **On ship build and on save migration,** every combat hull's required slots are auto-filled with a free Standard-Issue baseline: a `Standard-Issue Autocannon` (or the hull's default weapon), a `Standard-Issue Shield Emitter`, and `Standard-Issue Hull Plating`. These are stat-real but sit at the bottom of the power curve (quality 0, neutral rolls), exactly mirroring the 0.11.0 Standard-Issue precedent for economy slots. A fresh or migrated ship is therefore ALWAYS dispatchable. Never bricked.
- **The blocker fires only on a stripped slot.** If a player uninstalls the Standard-Issue (or crafted) item from a required slot and leaves it empty, `canDispatchPatrol` (`tick.ts`) returns a clear reason: "No weapon installed" / "No hull plating installed" / "No shield emitter installed." This is the "without hull plating you die" gate, and it can only be reached by deliberate player action.
- **Weapons exemption nuance.** The 0.13.0 design made weapons exempt from the never-empty rule (a ship could fly unarmed). This epic OVERRIDES that for combat hulls specifically: a combat hull needs at least one weapon to patrol. A non-combat hull is unaffected (it cannot patrol anyway).

`DECISION 3a.` Confirm the required-slot set is exactly {>=1 weapon, shield, hull plating}. Alternative: also require a reactor with enough power output once the power budget (Section 10) is live, which would make an over-fitted ship blockable on power. Recommend NOT gating dispatch on power in 1.0 (power gates FITTING, not dispatch) to keep the blocker legible.

## 4. Weapons as craftable, rolled items

Weapons move from static `WEAPON_DEFS` templates into the itemgen pipeline while keeping their family/triangle/signature identity.

- **Base type stays authored.** The nine weapon defs (family, triangle ownership, signature levers, base range, base projectile count, effect-slot identity) remain the authored "base item." Itemgen rolls the VARIABLE stats on top.
- **Itemgen mapping.** A crafted weapon's `quality` (0 to 5), `rarity`, and `iLevel` drive: `weaponYield` (min-max), `weaponAccuracy`, durability ceiling, crit chance/multiplier, and the proc chance / escalation of its two effect slots. This reuses the exact budget-share + affix mechanism `itemgen.ts` already implements for economy gear.
- **Effect slots roll from the disruption pool.** Each weapon carries two effect slots; the base type fixes the signature-aligned one (Plasma always rolls Plasma Fire, Voltaic always anti-shield disruptions) and rarity can add/upgrade the second, exactly as the epic S6d described. This is also how the currently-sourceless effects (Section 8) get a home.
- **`makeWeaponInstance` becomes a roll, not a clone.** Today it is a flat template copy at quality 0 (`weapons.ts:340`). It becomes an itemgen mint that produces a real `EquipmentInstance` with rolled combat stats.
- **Hardpoint + install caps.** The existing `installCap` and class-restriction fields (already first-class on the weapon def) start enforcing: top-tier weapons cap at 1 mounted, class gates block a weapon on the wrong hull. These were "forward hooks wired in v1"; this epic activates them.

`DECISION 4a.` Weapon durability: today durability is a shared constant (`BASE_WEAPON_DURABILITY`). Recommend quality drives the ceiling (higher quality = more durability + lower per-hit loss chance), per the epic durability model. Confirm this is desired over a flat ceiling.

---

## 5. Shield emitters as items

- New `shieldEmitter` singleton slot. Implicit lines: `shieldCapacity` + `shieldRecharge` (the two the sim already reads off the hull). Rolled affixes can add `shieldCoherence` (attenuation resist, currently hardcoded 0) and per-family shield resist.
- **Hull base vs gear.** `DECISION 5a.` Two models: (i) the shield emitter is the SOLE source of shield capacity (hull contributes none; a stripped shield slot means literally zero shields, which is why it blocks), or (ii) the hull contributes a small base and the emitter multiplies/adds. Recommend (i) pure-gear for shields: it makes the blocker physically meaningful ("no emitter, no shields") and matches the user's mental model ("no shield emitter installed, the ship has no shield capacity"). The Standard-Issue emitter provides a baseline so a default ship still has shields.

---

## 6. Hull plating as items

- New `hullPlating` singleton slot. Implicit line: `hullStrength` (adds to hull integrity). Rolled affixes: `ablativeArmor` (flat energy soak buffer), `kineticDampening` (flat kinetic % reduction), per-family hull resist, optional small auto-repair. Every one of these is a stat `resolveBattle.ts` already consumes and currently receives as 0.
- **Hull base vs gear.** `DECISION 6a.` The user said "without hull plating you have no hull integrity." Taken literally that means the hull class contributes ZERO structural HP and armor gear is everything, which is a big departure (today `hullIntegrity` is a hull property). Two models: (i) literal, hull plating is the sole source of hull HP (stripped = 0 = you die instantly = blocker is physical), or (ii) the hull has a small intrinsic frame HP and plating is the bulk + all mitigation. Recommend a middle path: the hull keeps a SMALL intrinsic frame integrity (so "hull" as a chassis still means something and the sim never divides by zero), plating provides the MAJORITY of effective HP plus all armor/dampening/resists, and a stripped plating slot is a hard dispatch blocker anyway (Section 3) so the "you'd die" intent is honored by the gate, not by a zero-HP ship. This avoids edge cases (a bug that strips plating mid-battle should not instakill) while keeping the fiction. Needs your call.

## 7. Defensive stat wiring map

Once Sections 5 and 6 exist, `shipToCombatant` (`bridge.ts:314-325`) stops hardcoding and reads real inputs. The full map:

| Combatant stat | Today | Wired to |
|---|---|---|
| `hull` / `hullMax` | hull class | hull frame + `hullPlating.hullStrength` |
| `shield` / `shieldMax` | hull class | `shieldEmitter.shieldCapacity` |
| `shieldRecharge` | hull class | `shieldEmitter.shieldRecharge` |
| `shieldCoherence` | 0 | `shieldEmitter` affix |
| `ablativeArmor` | 0 | `hullPlating` affix |
| `kineticDampening` | 0 | `hullPlating` affix |
| `evasion` | 0 | hull maneuver stat + FTL/thruster gear + talents, range-modified |
| `damageResist{family}` | zero-map | `hullPlating` / resist affixes |
| `disruptionResist{family}` | zero-map | `hullPlating` / resist affixes |
| `speed` | `DEFAULT_COMBAT_SPEED` | hull maneuver stat + FTL gear |

`DECISION 7a.` Evasion + speed source: recommend they derive from a hull `maneuverability` base stat (already reserved in `RESERVED_STAT_KEYS`) plus the FTL drive gear the ship already has, rather than inventing a new slot. Confirm.

## 8. Status effect completion (7 dormant effects)

The disruption engine is built; 6 of 13 effects are live. Plan for the other 7:

- **Emitter Overload (+damageTaken) and Weapon Jam (weaponOffline): wire the READER.** These already proc from Voltaic / EMP Cannon and show a pip, but the outcome path never reads them (a shown lie, close to a correctness bug). `applyProjectileDamage` gains a `damageTaken` multiplier lookup; the firing gate checks `weaponOffline` alongside durability. This is the smallest, highest-value fix and can be done early in Phase 1 even before full gear.
- **Sensor Power Drain (-range), Coil Dampening (-weapon damage), Harmonic Gap (+attenuation): give them a SOURCE.** Readers exist (or are trivial); they have no weapon that inflicts them. Assign each to a weapon effect slot via Section 4's roll (e.g., Coil Dampening on an EW weapon; name the pending one now). Harmonic Gap also needs its `attenuation` statDelta read by the mitigation split.
- **Inhibit (-drone attack rate): wire in Phase 2** alongside real drone loadouts (no point before drones vary).
- **Overcharged Capacitors (buff): build the buff-apply path in Phase 3.** No buff is applied anywhere today because support drones + modules (the buff sources) are not live. This is the one effect that legitimately waits for its source.

Net target: all 13 effects live and honest by end of epic; 12 of 13 by end of Phase 2.

## 9. Drone content pipeline (Phase 2)

The S8 drone AI matrix is fully coded and tested; every carrier just flies one hardcoded tier-0 Attack squadron. Phase 2 builds the content + fitment layer that lets a player compose a screen.

- **Drone pods as items.** A `DronePod` becomes a craftable `EquipmentInstance` (the type + `makeDronePod` already exist as test-only shells). One pod = one squadron of one role (attack / defense / support). Fabricated at type-specific lines, stored in the Warehouse, fitted to a bay while the ship is parked. Reuses the Fabricator to Warehouse to fit pipeline wholesale.
- **Hangar bays become a real capacity.** `builtInBays` stops being a decorative label. A carrier has N built-in bays + M more from a fitted hangar system; each bay holds one pod. Non-carriers have 0.
- **The dormant behaviors light up** simply by having defense/support squadrons reach the battlefield: deflect, particle reflect, smart-reflect (flip the hardcoded `false`), meat-shield overflow, support hull-repair pulse + disruption cleanse, and hangar-tier squadron scaling (callers stop passing tier 0). No new sim code, just real inputs, exactly like the stat wiring.
- **In-combat replenish** stays a module unlock (Phase 3); between-wave replenish already works.
- `DECISION 9a.` Pod-as-slot vs pod-as-nested. Recommend pods are `EquipmentInstance`s with a `droneBay` slot type and a bay index, so they reuse install/uninstall wholesale. Confirm.

## 10. Modules and the active-ability engine (Phase 3, the new architecture)

This is the one part of the epic that is genuinely new sim architecture, not "feed the engine real numbers." It is deliberately last and isolated.

- **A module is a stat-stick + an optional active ability.** The stat-stick half is pure itemgen (like any other gear). The active-ability half needs a deterministic trigger/effect model inside the sim.
- **Bounded trigger taxonomy (`DECISION 10a`).** To keep it deterministic and cheap, active abilities fire only from a small fixed set of triggers, resolved at known points in the step loop:
  - `onBattleStart` (e.g., a pre-charge buff)
  - `onIncomingAmbush` (Particle-Trace Detector: chance to pre-raise shields)
  - `postAmbush` (Rapid-Charge / Combat-Reflex: shorten the post-ambush fire delay)
  - `passivePerTick` (in-combat drone replenish %; a small hull auto-repair)
  - `onThreshold` (e.g., "below 25% hull, one shield surge") if we want a reactive one
  No free-form scripting, no player-timed activation (idle-native, everything auto). This taxonomy is the key thing to sign off, because it bounds the whole subsystem.
- **v1 module roster:** Rapid-Charge, Particle-Trace Detector, in-combat drone replenish module, plus 2 to 3 stat-stick modules. The reserved buff `Overcharged Capacitors` becomes a module/support-drone proc here.
- **Power budget goes live.** Reactor `powerOutput` vs total fitted `powerDraw` becomes a FIT-TIME gate (you cannot install more than your reactor powers). This is fit-time only, not a dispatch blocker (Section 3a).

## 11. Enemy stat model (the balance keystone)

`DECISION 11a` (the biggest design fork in the epic). Once players field rolled, geared, variable stats, the hardcoded enemy hulls (`enemyHulls.ts`) are either trivial or brick walls. Three options:

1. **Enemies roll gear via itemgen (symmetric).** Most emergent, hardest to balance and tune, most parity surface.
2. **Hand-authored enemy stat curves per difficulty tier.** `enemyHulls.ts` stays authored, expanded, and scaled by a difficulty knob. Fully controllable, least emergent.
3. **Hybrid (recommended): authored enemy loadout TEMPLATES + a difficulty scalar.** Each enemy hull references real weapon defs and a stat budget authored as a fraction of an equivalent player fit, then a single per-tier difficulty scalar (the T-I..T-X seam already reserved in `enemyWave.ts`) scales the whole encounter. You tune ONE knob per tier, not a loot table, and enemies use the same real weapons/effects the player faces (so the triangle and resists matter both ways) without the noise of full random rolls.

Recommend option 3. It gives deterministic, tunable difficulty, reuses the reserved difficulty-tier seam, and keeps the rebalance-per-phase gate (Principle 4) tractable. This decision drives the entire rebalance workload, so it needs an explicit call.

## 12. Loot completion

The reserved "Damaged [System]" reverse-engineering drop (`patrolLoot.ts:29`) was omitted because there was no weapon/gear crafting to feed it (it would be dead inventory). Once Section 4 exists, wrecks can drop a `Damaged [Weapon/Shield/Plating]` that salvages into build materials, exactly like the existing Damaged Reactor Housing idiom. Turns on in Phase 1 (weapons) and expands in Phase 2/3. No functional gear drops from wrecks (protects the crafting loop, per the 0.13.0 design).

## 13. Battle Rating + Engagement Forecast UI

`rating.ts` already computes both; they have no UI. Surface Battle Rating on ship cards (a "how geared am I" scalar) and Engagement Forecast (win-% vs a specific patrol's enemies, run through the real sim) on the Patrol dispatch card. Both advisory. This is UI-only and MOCKUP-GATED per the project's visual-UI rule; it lands in Phase 3 with the other readouts, or earlier if the gear phases make players ask "am I ready."

---

## 14. Durability + repair extension

Combat gear wears like the reactor/FTL systems already do. Worn combat gear repairs at the Shipyard, folding into the existing repair-bay loop, for a % of its craft materials. Mostly an extension of built behavior. The Shipyard repair-bay design (S13: >=1 bay reserved for repair) is already partially shipped; this epic completes it for combat gear.

---

## 15. Rebalance approach

- Each phase ends with a rebalance pass against that phase's new inputs, then play, then next phase (Principle 4).
- The primary knob is the Section 11 enemy difficulty scalar. Secondary knobs: durability constants (already tuned once, `72d0b71`), wave counts, Standard-Issue baseline power level.
- Because we hold for one debut, the FINAL balance is what ships; internal phase gates keep each phase playable and testable so the final tune is not a cliff.

---

## 16. Save migration

Simplified by the hold-for-one-debut decision: no combat has ever shipped to prod, so there is no live-combat save shape to migrate. The migration path is pre-combat (0.12.1-shaped) save to combat-1.0 save:

- Add fitted-combat-gear fields to the ship model; on load of a pre-combat save, auto-install the Standard-Issue combat baseline on every combat hull (Section 3).
- Add drone-pod, module, repair-queue, captain-counter, and faction fields as the phases introduce them.
- `DECISION 16a.` One `SAVE_VERSION` bump per phase (smaller, individually testable migrations, audit flag #4) vs one bump at the debut. Recommend one bump per phase on the branch; since it never hits prod until the end, the intermediate versions only ever exist on devpreview, and the final prod migration is still a single clean jump from 0.12.1. Best of both.

## 17. Parity discipline

Every phase re-greens the 100-test offline-vs-live parity fuzz before it is done (Principle 3). New display-only additions (Battle Rating, tooltips) must stay outcome-neutral and off the combat RNG stream. Any change to a rolled stat, effect, or drone behavior gets a parity test before it is considered wired.

## 19. Phase breakdown

- **Phase 1 (Gear-driven combat):** Sections 1 through 8 and 12. Combat gear as items, Standard-Issue baseline, dispatch blocker, all defensive stats wired, 12 of 13 effects live, weapon-crafting loot, enemy stat model (Section 11) + rebalance #1. After this, combat is fundamentally gear-driven.
- **Phase 2 (Drone content):** Section 9. Pods as items, hangar bays, dormant drone behaviors live, Inhibit wired, rebalance #2 (carriers).
- **Phase 3 (Modules + readouts):** Sections 10 and 13. Active-ability engine, counter-modules, power budget, buff-apply path (13/13 effects), Battle Rating + Forecast UI, rebalance #3.
- **Debut:** one complete prod promotion after Phase 3, single clean 0.12.1 to combat-1.0 migration.

## 21. Explicitly deferred (Tier B, stays out of 1.0)

Restated from the completeness audit so the boundary is a decision, not an accident: specialty weapons beyond the nine, escort missions, combat in non-combat missions, player-side cloaking, captain/crew/ship destruction + death, faction reputation payoff, set-bonus resolution, weapon/captain proficiency, refit + configurable bay allocation, the 2.0 interactive turn-based Battlespace, boss encounters, multi-ship fleets, the other six hull classes, ground/away-team combat. All hooks stay forward-wired; none is built in 1.0.
