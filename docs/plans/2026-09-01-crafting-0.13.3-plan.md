# Facilities / Crafting (0.13.3) : Build Plan

Companion to `2026-09-01-crafting-0.13.3-design.md`. Branch `feat/crafting-0.13.3`.

**Method:** subagent-driven-development per unit (implementer, then spec review, then code-quality review), branch-direct commits, one concern per commit. **Every unit gates green before commit:**

```
npm run check      # 0 errors. The 2 pre-existing RadialWeb a11y warnings are expected and stay.
npx vitest run     # full suite green
npx vitest run -t "parit"   # EXACTLY 101
```

A unit that cannot go green does not get committed. A unit that turns parity red is reverted, not patched forward.

**Ordering principle: engine before pixels.** The queue promotion pass, the salvage process conversion and the crafting XP math are all pure functions of state and are node-testable with no DOM. They land first, with heavy unit tests plus new parity cases, so the UI in phases 4 to 6 is built on an engine that is already proven. This is deliberate risk order: the parity invariant is the thing that cannot be visually spot-checked, so it must be defended by tests written before any console is opened.

**Parity is the top invariant.** Any unit that touches `resolveProcesses`, `economyTick`, the queue promotion pass or the salvage RNG states its parity argument in its Approach and calls out parity 101 in its Gate. The existing 101 cases are never edited, never renamed and never skipped. New parity cases are additions on top.

**Line numbers drift.** Every anchor in the design doc and in this plan is a current-tip line number that will move as soon as the first unit commits. **Re-locate by content** (the function name, the comment header, the string literal), never by line number. If a unit's stated anchor does not match, that is expected: find the construct and proceed.

**Terminology.** INSTALL / INSTALLATION for gear in all new copy. Never fit, fitting or fitment. Sweep each console for stragglers while it is open.

**No em dashes** in code, comments, docs or player-facing copy. Colons, periods, parentheses.

## Phase peel points

The release is grouped into phases so later phases can peel into 0.13.4 if it grows. Phases are ordered so the branch is a coherent, shippable release at every peel point.

| Phase | If we ship here, this goes out | If we stop here, this defers to 0.13.4 | Peel verdict |
|---|---|---|---|

| **1. Queue engine core** | Nothing player-visible. Dormant engine + SAVE_VERSION 40 + the queue talent chain (learnable, no effect yet). | The whole feature. | **Do not peel here.** Foundation only. |

| **3. Crafting XP + iLevel** | A crafting-progression rebalance (weighted XP, new curve, the iLevel talent) with a dormant queue engine underneath and no UI to explain it. | The queue, auto-salvage, the UX pass. | **Not recommended.** Shippable as a balance patch, but the headline feature is invisible and the rebalance lands unexplained. Only if the release must close early. |
| **4. Queue + salvage UI** | The full headline release: queue on Refinery, Fabricator and Salvage Bay; timed salvage; the crafting XP rebalance made visible; queue-aware Facilities dashboard with attention dots. | Auto-salvage rules; the six-console presentation pass. | **RECOMMENDED FALLBACK PEEL.** This is a complete, coherent, valuable 0.13.3 on its own. |

**How to peel:** stop after the last committed unit of the chosen phase, then jump straight to Phase 7 and re-scope the QA sheet and patch note to what actually shipped. Do not leave a half-built unit on the branch. Move the deferred phases into a `2026-09-XX-crafting-0.13.4-plan.md` stub before closing.

## Assumptions this plan makes (the design left these open)

These are decisions the plan had to take to be buildable. Each is cheap to reverse. Raise any the user disagrees with before Phase 1 Unit 3.

1. **Module placement and dependency direction.** `QUEUE_ADAPTERS` and the promotion pass live in **`tick.ts`**, beside `PROCESS_XP_AWARDS` and the four existing tail passes, because the refine and fabricate adapters delegate to `canStartLine` / `startLine` which already live there. `src/lib/game/craftQueue.ts` stays a **read-only view model** that imports from `tick.ts` (never the reverse), so there is no import cycle. The design's phrasing puts "the promotion candidate scan" in `craftQueue.ts`, which would invert the dependency; the scan predicate is exported from `tick.ts` and `craftQueue.ts` consumes it, so the UI and the engine still cannot disagree.
2. **Function name collision.** `GameState.processQueue` (the array) and an exported `processQueue(state)` (the pass) cannot share a name legibly. The pass is named **`promoteQueuedOrders(state)`**.
3. **`SalvageTargetRef` is never defined in the design.** Assumed: `{ kind: "equipment"; instanceId: string } | { kind: "material"; itemId: string } | { kind: "ship"; shipId: string }`. Plain strings only, so the save carries no Decimal.
4. **Salvage Bay slot count.** The design says the Salvage Bay gets "its own new slot count" but never gives a value or a home. Assumed **`SALVAGE_SLOT_COUNT = 1`**, a module constant with **no upgrade track this release** (the Salvage Bay is one of the three non-leveled facilities per preservation inventory 1a, and adding a level track to it is scope the design did not ask for). Queue depth, not slot count, is the Salvage Bay's throughput knob this release.
5. **Queue mutation API.** Implied by the UI, never specified. Assumed three pure exported functions: `enqueueOrder`, `removeQueuedOrder`, `moveQueuedOrder`, all returning the same reference on a no-op, all enforcing the depth cap at enqueue.
6. **Auto-salvage duplicate rule.** Section 7.6 says "same `slotType` + `varietyKey`, keep the best `keepPerVariety`"; section 14 item 3 resolves it as "same blueprint + same slot, KEEP THE BEST". **Section 14 wins** (it is the later user resolution): the key is blueprint key + slot type, and exactly one best is kept. The `keepPerVariety` field stays in the save shape fixed at 1 and is **not** user-editable this release, so a later release can expose it with no migration.
7. **Auto-salvage rule combination.** The interaction between `maxQuality` and `duplicates` is unspecified. Assumed **OR**: a spare matching either enabled rule is a candidate, with every safety exclusion (installed, reserved, baseline, confirm-ON quality) applied afterward as a filter.
8. **Salvage XP axes.** Still listed as open. Assumed the design's recommendation: `salvageJob: { fleetAdmin: false, crafting: false }`. This is a one-line change plus one test if the user rules otherwise.
9. **Promotion policy.** Still listed as open. Assumed the design's recommendation: **skip-on-block**, array never reordered.
10. **XP visibility.** Still listed as open. Assumed the design's recommendation: per-recipe XP award on Refinery and Fabricator rows plus a crafting level panel.
11. **Modal extraction.** Still listed as open, and SUGGESTIONS blocks it. Assumed **mirror the 0.13.2 `ss-modal` pattern locally**, no shared `<Modal>` component extracted this release.
12. **Continuous lines are enqueueable.** Allowed, with the mandatory warning label from design 5.4 shown on the continuous option in the configurator and on the queued row.
13. **Auto-salvage runs before promotion inside the same pass**, so a rule-added order can promote the same tick. This matches the existing "a slot freed this tick is refilled this tick" behavior.
14. **Reorder is per-facility, applied to the flat array.** The queue array is flat across facilities but the UI shows one facility's rows. "Move up" swaps with the previous entry **of the same facility** in the flat array, leaving other facilities' entries untouched. This needs its own test.
15. **Salvage result history is derived, not persisted.** The Last Salvage readout becomes a per-job result list built from the **existing event log** entries the completion branch writes, so no new persisted array and no extra save field. If that proves too lossy in Phase 4, escalate rather than quietly adding a state field after the migration has landed.

# PHASE 0: Groundwork

Shippable on its own. Fixes a live papercut and touches nothing else.

### Unit 0.1: Captain-page return path (`shipsReturnTo`)
- **Goal:** the captain page's Ship Systems shortcut gets a return path. Today it sets `selectedShipId` + `shipsView = "ship"` + `activeTab = "ships"`, and both the Back control and the loadout board's `onClose` drop the player on the **ships roster**, not back on the captain they came from. This is the one genuine accidental side effect the 0.13.2 regression audit found (design section 14 item 4).
- **Files:** `src/App.svelte`. Re-locate by content: the Ship Systems shortcut button in the captain console (search `Ship Systems shortcut`), the ship-detail Back control (search `Back to ships roster`), the `ShipSystemsPanel` `onClose` handler in the ship-detail branch, and the nav-state declaration block near `shipsView` / `selectedShipId`.
- **Approach:** add one plain let `shipsReturnTo: { captainId: string } | null = null` beside `shipsView` / `selectedShipId`, declared with a comment explaining the marker. The captain shortcut sets it to the originating captain before navigating. Back and `onClose` branch: when the marker is set, clear it and restore `activeTab = "personnel"`, `personnelRosterView = "captain"`, `activeCaptainIndex` resolved **by captain id** (not by the stale index, which can move if the roster changes) with a fallback to the roster grid when the captain no longer exists; otherwise keep today's behavior exactly (roster grid + `pendingFocusShipId`). Any entry into the Ships tab that is **not** the captain shortcut clears the marker, so it can never go stale: clear it in the ship-detail row-open handler and on the vanished-hull guard. Do not touch `pendingFocusShipId` semantics on the non-marker path.
- **Preservation carried:** the captain page's disabled-with-reason on the shortcut ("This captain has no assigned ship") is untouched; the loadout board remains the single equip surface with both entry points landing on the same board.
- **Gate:** the three commands. Parity 101 trivially (no engine touch). Manual check: captain to Ship Systems to Back returns to that captain; roster to ship to Back returns to the roster with focus restored; deleting or reassigning the captain mid-flow falls back cleanly.

**PEEL POINT 0.** Ships: the return-path fix. Defers: everything. Only if the release must abort immediately.

# PHASE 1: Queue engine core (pure, no UI)

Foundation. Nothing here is player-visible except a learnable talent that does nothing yet, which is why this phase is not a peel point.

### Unit 1.1: SAVE_VERSION 39 to 40 (additive migration + round-trip test)
- **Goal:** the new save fields land **first**, because every later unit reads them. Purely additive, no existing field is touched or recomputed.
- **Files:** `src/lib/game/save.ts` (`SAVE_VERSION`, the `MIGRATIONS` table, `hydrateDecimals`), `src/lib/game/model.ts` (the `GameState` interface + the initial-state factory), `src/lib/game/save.test.ts`.
- **Approach:** bump `SAVE_VERSION` to 40 and add `MIGRATIONS[39]` in the shape of the existing rows (`36` and `38` are the closest templates): spread the state and default the three new fields.
  - `processQueue: []`
  - `nextQueueId: 1`
  - `autoSalvage: { enabled: false, maxQuality: null, duplicates: false, keepPerVariety: 1 }`
  Add the same three to the fresh-game initial state so a new save and a migrated save are identical in shape. **Verify explicitly that `hydrateDecimals` needs no new branch**: `QueuedJob` carries ids, string keys and plain numbers only, so it must not gain a Decimal now or later without a hydrate branch. Add a comment on the `QueuedJob` interface saying exactly that, because it is the difference between a one-line migration and a serialization bug (design section 10).
  `craftingLevel` / `craftingXp` are **not** touched. Grandfathering is a design decision, not an oversight, and the migration carries a comment saying so.
- **Gate:** the three commands, plus a new round-trip test: a v39 fixture loads, migrates to 40, serializes and re-loads deep-equal; a v40 save skips the migration; a fresh game already has the fields. Parity 101 (no tick behavior change at all).

### Unit 1.2: Queue depth talent chain + `queueDepth` helper
- **Goal:** the talent data and the derive-on-read depth helper, with no consumer yet.
- **Files:** `src/lib/game/model.ts` (`HomeworldTalentEffect` union, the `HOMEWORLD_TALENTS` table, `QUEUE_DEPTH_BASE`, `queueDepth`), `src/lib/game/talentWeb.test.ts` or a new `craftQueue.test.ts`.
- **Approach:** add `{ type: "queueDepth"; depth: number }` to `HomeworldTalentEffect` and three adjacency-linked nodes `fleetLogisticsQueue1/2/3` mirroring `fleetLogisticsSlot1/2/3` in shape, cost and `requiresFleetAdminLevel` walls. `queueDepth(state)` **sums** learned nodes rather than short-circuiting, exactly as `salvageTalentBonus` sums `salvageBoost` and as `MAX_UNLOCKABLE_CAPTAINS` counts nodes, so a fourth node later needs zero engine change. Base is 1 per design section 14 item 2. Adding a union member may light up exhaustive switches over `HomeworldTalentEffect`: handle every one explicitly rather than adding a default case.
- **Approach note (no migration):** talents are stored by key, so three new keys need no migration. Confirm that in the unit's commit message.
- **Gate:** the three commands, plus tests: base depth with no talents is 1; each node adds exactly 1; all three learned gives 4; an unknown key in `unlockedHomeworldTalents` does not throw; the RadialWeb still renders all five branches (existing talent web tests stay green).

### Unit 1.3: Queue mutation API + `QUEUE_ADAPTERS` (no tick wiring)
- **Goal:** everything needed to hold and validate a queue, still not connected to the tick. This is the unit that can be reviewed purely on its tests.
- **Files:** `src/lib/game/model.ts` (`QueueFacilityKey`, `QueuedOrder`, `QueuedJob`), `src/lib/game/tick.ts` (the `QueueAdapter` type, `QUEUE_ADAPTERS`, `enqueueOrder` / `removeQueuedOrder` / `moveQueuedOrder`), new `src/lib/game/craftQueue.test.ts`.
- **Approach:**
  - `QUEUE_ADAPTERS: Record<QueueFacilityKey, QueueAdapter>` sits in `tick.ts` beside `PROCESS_XP_AWARDS`, with the same comment explaining that the `Record` is exhaustive **on purpose**: adding a `QueueFacilityKey` without a row is a compile error. The `salvageBay` row is stubbed here with a `canStart` that always returns a "not implemented yet" reason and a `start` that returns `{ next: state, started: false }`; Phase 2 Unit 4 replaces it. Stubbing keeps the table exhaustive without pulling salvage forward.
  - `refinery` and `fabricator` adapters **delegate wholesale** to `canStartLine` / `startLine`. Zero new gate logic, so the queue can never disagree with what the configurator's Start button says. `hasFreeSlot` is the only per-facility divergence: `refineSlotCount` vs `refineLines.length`, `fabricateSlotCount` vs `fabricateLines.length`.
  - Mutation functions are pure, return the same reference on a no-op (the `startProcess` idiom), and enforce `queueDepth(state)` **per facility** at enqueue by counting matching entries. `moveQueuedOrder` swaps with the neighbouring entry **of the same facility** in the flat array (assumption 14).
- **Approach, parity:** nothing in this unit runs in the tick, so parity is preserved by construction. Say so in the commit message rather than leaving it implied.
- **Gate:** the three commands, plus tests: enqueue respects per-facility depth and rejects past it; enqueue past depth returns the same reference; remove by id; move up/down at the boundaries is a no-op; move only reorders same-facility neighbours and leaves interleaved other-facility entries in place; ids mint monotonically from `nextQueueId`; the adapter table has a row for every `QueueFacilityKey`.

### Unit 1.4: `promoteQueuedOrders` in the `economyTick` tail (the parity unit)
- **Goal:** the promotion pass, wired at the one correct seam, with parity proven rather than argued.
- **Files:** `src/lib/game/tick.ts` (`promoteQueuedOrders` + its call site in `economyTick`), `src/lib/game/craftQueue.test.ts`, a new parity test file or additions to the existing craft-line parity cases.
- **Approach:**
  - The pass runs **inside `economyTick`, after `resolveProcesses` and before `processRefineLines`**, so an order promoted this tick is stepped by the line engine the same tick, exactly as a slot freed by a completion is refilled the same tick today. It is **never** called from a UI handler, no matter how responsive that would feel (design risk 1 names this temptation explicitly).
  - Iterate facilities in the **fixed declared `QueueFacilityKey` union order**, never `Object.keys` over a runtime map. Within a facility, scan the array in index order while `hasFreeSlot` holds; promote the first entry whose adapter `canStart` returns ok; **skip blocked entries without reordering the array**. A skipped entry keeps its position and is retried first next tick.
  - **Promotion draws no RNG.** Every promotion is a `startProcess` (deduct at start); every RNG draw still happens at completion inside `resolveProcesses`. State this in the function's header comment, because it is the property that keeps the RNG stream position untouched by this phase.
  - **Parity argument, stated in the code comment and in the review:** closed form holds **by construction**, not by reasoning. `tick()` steps an offline span as `economyTick(next, 1, rng)` per whole tick and the live poll calls `economyTick(state, 1)` per whole tick, so the pass runs exactly once per tick on both paths. The known bounded trailing-fractional artifact documented in `tick()` applies to this pass identically to the four existing tail passes: at most one extra promotion on a sub-tick span, self-correcting next whole tick. No new class of divergence, and the pass must not make the existing artifact worse.
- **Gate:** the three commands, **parity must read exactly 101** (the existing cases are untouched), plus these NEW parity cases:
  1. `economyTick` stepped one tick N times with a loaded queue is deep-equal to the same start advanced by `tick(N seconds, ...)`.
  2. A queue draining across a long offline span promotes the same orders in the same sequence as live stepping.
  3. A queue whose head is unaffordable at tick k and affordable at tick k+m promotes at exactly k+m on both paths.
  4. Skip-on-block: a blocked head does not idle the facility when a later entry of the same facility can run, and the array order is unchanged afterward.
  5. Facility iteration order is stable across runs.
- **Review focus:** that the call site is in `economyTick`'s tail and nowhere else; that no UI handler calls it; that the array is never sorted or reordered by the pass.

### Unit 1.5: `craftQueue.ts` pure view model
- **Goal:** the read-only derivation the Phase 4 UI will bind to, landed and tested before any UI exists.
- **Files:** new `src/lib/game/craftQueue.ts` + `craftQueue.test.ts` (extend the file from 1.3).
- **Approach:** pure functions only, no state mutation, in the shape of `shipRoster.ts` / `homeDashboard.ts`: per-facility used/free depth, the ordered row model (position, recipe or target label, mode, a live block reason resolved through the existing `startLineBlockText` seam), and "what would promote next". **Blocked state is derived every read, never stored**, matching `stepCraftLine`'s deliberate choice to drop the retired `pausedReason` bookkeeping. Imports from `tick.ts`; `tick.ts` never imports this (assumption 1). Keep it cheap: it runs every tick under the UI.
- **Gate:** the three commands, plus tests: row model ordering matches array order; block reason text matches what the adapter's `canStart` returned; used/free counts respect per-facility depth; empty queue at depth 0 vs depth available produce distinguishable models (the Phase 4 empty states depend on this).

**PEEL POINT 1.** Ships: nothing player-visible. **Do not peel here.**

# PHASE 2: Salvage as a queued process (pure, no UI)

The other half of the engine. Also not a peel point: the RNG move is landed but nothing can queue a salvage yet.

### Unit 2.1: Derived salvage reservations
- **Goal:** close the double-spend window without refactoring three proven salvage functions.
- **Files:** `src/lib/game/salvage.ts` (`salvageReservedInstanceIds`, `salvageReservedMaterialCount`), `src/lib/game/equipment.ts` (`canFitEquipment` reject reason), `salvage.test.ts`, `equipment.test.ts`.
- **Approach:** both helpers are **derived, never stored**, built by scanning `state.processQueue` for `salvage` orders plus `state.activeProcesses` for `salvageJob` effects. This is the same derive-on-read discipline `allocatedItem` uses and it cannot go stale. `canFitEquipment` gains a `queuedForSalvage` reject reason so a reserved instance cannot be installed out from under its job. **Centralize the check behind the existing `canFitEquipment` seam** rather than scattering it: design risk 4 says double consumption becomes possible the moment a new consumer of spare equipment skips this, so the seam is the defense.
- **Approach, order:** this unit lands **before** anything can create a `salvageJob`, so both helpers return empty and `canFitEquipment` is unchanged in behavior. That is intentional: the guard exists before the thing it guards.
- **Gate:** the three commands. Parity 101 (nothing in the tick path changed). Tests: both helpers return empty on a save with no salvage work; a reserved instance is rejected by `canFitEquipment` with the specific reason; the reject reason is distinct from every existing one.

### Unit 2.2: The `salvageJob` kind, effect, XP row and duration
- **Goal:** the model surface for a timed salvage, with no reference from `tick.ts` into `salvage.ts` yet (so the existing grep guard stays green and honest for one more unit).
- **Files:** `src/lib/game/model.ts` (`TimedProcessKind` + `"salvageJob"`, `ProcessEffect` + `{ type: "salvageResolve"; target: SalvageTargetRef }`, `SalvageTargetRef`, the duration constants), `src/lib/game/tick.ts` (`PROCESS_XP_AWARDS` row), a duration test.
- **Approach:** adding the kind **forces** a `PROCESS_XP_AWARDS` row because the `Record` is exhaustive. The row is `salvageJob: { fleetAdmin: false, crafting: false }` (assumption 8), with a comment giving the reason: salvage returns 30 to 40 percent of inputs, so an XP award would make craft-then-salvage-then-craft a net XP faucet, which is exactly why `fuelRefineJob` and `shipRepair` are already excluded. Duration is a pure exported function:
  ```
  salvageDurationTicks = ceil( SALVAGE_BASE_TICKS(5) + iLevel * SALVAGE_TICKS_PER_ILEVEL(0.5) + quality * SALVAGE_TICKS_PER_QUALITY(2) )
  ```
  with a flat `SALVAGE_MATERIAL_TICKS` (5) for a loot roll and one third of `buildRecipe.durationTicks` for a hull teardown (which finally delivers the timed teardown the `salvageShip` header has been waiting for). Every constant is marked first-pass tunable in a comment, the way `CRAFTING_XP_PER_DURATION_TICK` is.
  **`salvageResolve` carries no Decimal**, so it passes the existing `"amount" in effect` hydrate guard untouched. Verify and comment it, same as Unit 1.1.
- **Gate:** the three commands. Parity 101. Tests: duration is a deterministic integer for every target kind; the XP row exists and is false on both axes; adding the kind did not break any exhaustive switch over `TimedProcessKind` or `ProcessEffect` (`npm run check` is the real proof here).

### Unit 2.3: The RNG move + the rewritten grep guard (one commit)
- **Goal:** salvage completes inside `resolveProcesses` on the **threaded seeded rng**, and the guard that protected the old boundary is rewritten to protect the new one **in the same commit**.
- **Files:** `src/lib/game/tick.ts` (the completion branch in `resolveProcesses`, plus `canStartSalvage` / `startSalvageJob`), `src/lib/game/salvage.ts` (the file-header parity-boundary note rewritten), `src/lib/game/salvage.test.ts` (the guard block, currently the "LIVE-ONLY, never wired into an economy-tick path" describe), a new salvage parity test.
- **Approach:**
  - The completion branch calls the **unchanged** `salvageEquipment` / `salvageSalvagedMaterial` / `salvageShip`, passing `resolveProcesses`' threaded `rng` in place of the `Math.random` default. The math is not touched (Omega 15a). Draw counts are already fixed and documented (1, 2 and 1 respectively), which is what makes the stream position predictable.
  - **Draw order rule:** salvage completions resolve in `activeProcesses` array order like every other completion, interleaved with the existing quality rolls exactly as the array dictates. `quality-roll.test.ts` is the template for the new test.
  - **Stale targets are a fail-safe no-op**: a hull already salvaged or lost, a vanished instance, a `lastShip` guard that now fires. The branch applies nothing, drops the process and writes an event-log line. Precedent: `clearShipDamage`'s documented "a stale shipId is a harmless no-op in the resolver".
  - `canStartSalvage` rejects a target that is already reserved (Unit 2.1), and **never consults `equipmentStorageCap`**: the escape-valve guarantee says the storage cap is never checked when recycling, so a full spare pool must still be able to queue. The in-flight piece keeps occupying its slot until completion, which is honest.
  - **The guard rewrite. Delete nothing; replace the proxy with the real invariant.** The current test asserts that `tick.ts` source does not contain `salvageEquipment` / `salvageSalvagedMaterial` / `salvageShip` / `./salvage`. That proxy becomes false while the invariant ("salvage never rolls on an unseeded stream inside the economy seam") must still hold. The replacement asserts:
    1. every salvage call site in `tick.ts` passes the threaded rng: `/salvage(Equipment|SalvagedMaterial|Ship)\s*\([^)]*\brng\b/` matches, and the match count equals the count of bare `salvage...(` occurrences;
    2. `tick.ts` introduces no new `Math.random` (the occurrence count is unchanged, or the salvage branch contains none);
    3. `salvage.ts` still imports nothing from `tick.ts` (direction preserved, no cycle).
    The rewritten guard **carries a comment naming the invariant it now defends**, because a guard whose purpose is not written down gets deleted by the next person who breaks it (design risk 3).
  - The `salvage.ts` file header's parity-boundary note is rewritten to describe the new boundary, not deleted.
- **Approach, parity:** this is the only unit in the release that changes RNG stream contents. Preservation argument: the stream position is determined by completion order, completion order is `activeProcesses` array order, and `resolveProcesses` already rebuilds survivors in original order (which is what the deep-equal parity test compares). Salvage adds draws at completion, in that same order, on both the live and offline paths. No draw happens at promotion or at start.
- **Gate:** the three commands, **parity exactly 101**, plus the NEW behavioral parity test that is the real proof: identical seeded states, one advanced N ticks one at a time and one advanced by `tick(N, ...)`, both with salvage jobs completing mid-span, produce deep-equal inventories **including quality buckets**. Plus: a stale target completes as a no-op and logs; a hull teardown on the last ship is refused or no-ops per the existing `lastShip` guard.
- **Review focus:** the guard rewrite is in this commit and not a later one; the guard's comment states the invariant; `salvage.ts` math is byte-identical.

### Unit 2.4: Salvage Bay slots + the real adapter row
- **Goal:** replace the Unit 1.3 stub so salvage can actually be queued and promoted.
- **Files:** `src/lib/game/tick.ts` (`SALVAGE_SLOT_COUNT`, the `salvageBay` adapter row), `craftQueue.test.ts`, a queue parity test.
- **Approach:** `hasFreeSlot` counts in-flight `salvageJob` processes against `SALVAGE_SLOT_COUNT` (assumption 4: constant 1, no upgrade track). `canStart` / `start` delegate to `canStartSalvage` / `startSalvageJob` from 2.3. Nothing else in the promotion pass changes: it still knows nothing about facilities.
- **Gate:** the three commands, parity 101, plus a new parity case: a Salvage Bay queue draining across an offline span promotes and completes in the same order and with the same loot as live stepping.

**PEEL POINT 2.** Ships: nothing player-visible. **Do not peel here.**

# PHASE 3: Crafting XP and iLevel (pure, no UI)

Small, independent, high value. Also the phase most likely to need a second balance pass after the queue is live (design risk 6).

### Unit 3.1: `craftingProgress.ts`, the pure XP and curve module
- **Goal:** all the new math in one pure, node-tested module before a single call site changes.
- **Files:** new `src/lib/game/craftingProgress.ts` + `craftingProgress.test.ts`; `src/lib/game/model.ts` for the constants and the optional `RefineRecipeDef.xpWeightNum` field.
- **Approach:**

# PHASE 5: Auto-salvage rules

Clean peel. Self-contained.

### Unit 5.1: Auto-salvage rule evaluation in the tick path
- **Goal:** the rules, evaluated where live and offline behave identically.
- **Files:** `src/lib/game/tick.ts` (inside `promoteQueuedOrders`), `src/lib/game/salvage.ts` or `craftQueue.ts` for the pure candidate selector, plus tests and a parity case.
- **Approach:** evaluated **in the tick path, inside the same pass**, before promotion, so a rule-added order can promote the same tick (assumption 13). It **reads state only and draws no RNG**, so it is closed form.
  - **Bounded per tick:** it may add at most `depth - queued` orders per facility per tick, so it can never flood the queue or the loop (Omega 14: bounded work, no unbounded loop in the tick).
  - **Deterministic candidate order:** candidates sorted by a stable key (instance id), never by iteration order over a map.
  - **Never touches:** installed gear (`fittedToShipId !== null`), anything already reserved, and **Standard-Issue baselines**. Baselines DESTROY for zero reward, and auto-destroying items is a data-loss shape, so baselines are excluded from auto rules entirely and Destroy stays a manual, deliberate act.
  - **Respects the per-quality confirm preference:** a quality tier whose `salvageConfirmQualities` checkbox is ON **cannot be auto-salvaged**. The player asked to be asked about that tier and an automation rule must not answer for them. This prevents the "it silently ate my Q4 drop" outcome. Note the wrinkle and handle it explicitly: `salvageConfirmQualities` lives in **localStorage** while the rules live in **`GameState`**, so the tick cannot read the preference directly. Thread the confirm-protected quality set into the tick as a parameter from the caller, or mirror it into the auto-salvage state at the point the player edits it. **Pick one, comment why, and make offline resolution behave the same as live**: a rule that behaves differently offline than live is a parity violation in spirit even if the deep-equal test passes.
  - **Duplicate rule** per assumption 6: same blueprint key + same slot type, keep the single best (iLevel, then quality, then rarity), auto-queue the rest.
- **Gate:** the three commands, **parity exactly 101**, plus new cases: rules off changes nothing; a bounded tick never adds more than `depth - queued`; candidate order is stable across runs; baselines, installed gear and reserved instances are never selected; a confirm-ON quality is never auto-queued; and an offline span with rules on produces the same queue and the same outcomes as live stepping.
