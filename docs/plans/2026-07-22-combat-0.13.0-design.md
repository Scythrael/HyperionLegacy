# Combat System (0.13.0) Design

> **For Claude:** This is the validated design from the 2026-07-22 brainstorm. Next step is `superpowers:writing-plans` to turn it into a phased implementation plan, then subagent-driven build. This is a LARGE multi-phase epic; the doc is the durable artifact that carries every decision forward across sessions.

**Goal:** A deterministic, headless, idle-native combat system driven from Patrol combat missions: ships with weapons/shields/hull/modules/drones fight seeded battles that resolve identically live or offline, narrated by a flavored combat log (and an optional visual mode), with real consequences (limp-home + Shipyard repair) and rewards (salvage, cargo loot, bounty, XP).

**Architecture:** A pure `resolveBattle(participants, seed) -> { outcome, log }` fixed-timestep simulator, integer/fixed-point math, two independent RNG streams (combat vs cosmetic). It supersedes the old two-tier plan (simple %-roll for missions + separate interactive Battlespace); one deep engine now serves mission auto-resolve, and a future 2.0 turn-based active mode layers on top of the same event stream.

**Tech stack:** Vite + Svelte 5 legacy `$:` reactivity, TypeScript, existing `model.ts` / `tick.ts` / `save.ts`, existing equipment/fabricator/storage systems, existing mission-dispatch model, RadialWeb talent trees, ShipSystemsPanel paper-doll, EquipmentTooltip.

**Reconciliation note:** This design honors and extends the prior `2026-07-17-ship-equipment-combat-epic-design.md` (weapon families/triangle, weapon roster, System Disruptions table + ranks, per-type resists, range bands, Battle Rating + Engagement Forecast, Dispatch Once/Repeatedly). Where the brainstorm went deeper or diverged, it is called out.

---

## 0. Governing principles (locked)

1. **Deterministic + seeded + headless.** A battle is a pure function of `(participants, seed)`. Same seed always yields the same outcome. It resolves with NO rendering (offline) and identically WITH rendering (live).
2. **Offline == live is a HARD invariant** (same discipline as the economy-parity invariant): the combat outcome must be byte-identical whether resolved during live play or offline catch-up.
3. **Two RNG streams.** A `combat` stream drives every outcome-affecting roll (hit/evade, crit, damage variance, wave rolls, loot). A separate `cosmetic` stream drives flavor-line selection only. Offline skips the cosmetic stream entirely; the result never changes. You can add/edit flavor text forever without altering a single outcome or breaking a replay.
4. **Integer / fixed-point math everywhere** (positions, cooldowns, HP, damage), never raw floats, to avoid cross-device drift.
5. **Bounded work.** Hard caps (max rounds per battle, max waves per patrol) guarantee offline catch-up terminates cheaply; no unbounded loops (Omega 14).
6. **Streamlined + clean.** Build efficient from the start so it does not become a processing nightmare. If profiling ever bites, simplify while preserving the result; goal is to not need to.
7. **Cap unused bits, build to scale.** Forward-wire hooks for deferred systems (sets/legendary affixes, reputation, crew, cloak) but do not build them until their patch. Same reserved-but-inert pattern the codebase already uses.
8. **The combat log is the single event stream** feeding three consumers: live watching, offline "while you were away" summary, and the future 2.0 replay/animation.
9. **No em dashes / no "--"** in code, comments, docs, or UI copy (CSS `var(--x)` exempt).

## 1. Sim core

A battle is `resolveBattle(participants, seed) -> { outcome, log }`.

- **Fixed 0.1s timestep** (combat's OWN internal clock, independent of the economy tick; step size is a tunable). Each step, in a deterministic combatant order:
  1. Advance movement: close/open 1D distance by `speed * dt`.
  2. Tick each weapon's **cooldown accumulator** with carry-over remainder (so fractional fire rates like 2.15/sec stay exact and never skew).
  3. For any weapon that both crossed its `secondsPerAttack` AND has its target in range, resolve a shot (Section 2), append event(s) to the log, apply results.
  4. Tick active status effects (DoTs, disruptions, buffs) (Section 4).
  5. Check deaths / destruction; evaluate the objective.
- **Teams + pluggable objective.** `[your ship (+escort later)]` vs `[enemies]`. Objective is data (Patrol: all-enemies-down = win; your-ship-down = loss).
- **"Round" = a 1-second narration bucket** for log pacing and DoT aggregation; the sim underneath is continuous at 0.1s. Live view streams ~1 round/sec.
- **Hard round/time cap -> tiebreak** (most hull % remaining) so two uncrackable tanks never loop forever.
- **Output:** `outcome` (win / loss + loss-detail) + `log` (ordered structured events; Section 16). Offline calls the same function but skips log/flavor generation, pure outcome + reward calc.

## 2. Shot pipeline

One shot resolves in this order (all rolls off the `combat` PRNG):

1. **Hit or evade.** `weaponAccuracy` vs target evasion (from maneuverability/speed + talents, modified by range). Miss narrates an evade line.
2. **Projectiles.** Weapon fires `weaponProjectileCount` shots, each rolling hit/crit independently (multi-projectile = reliable chip; single = swingy). Projectile count also matters vs drone screens (Section 8).
3. **Crit.** Each hit rolls crit (chance from weapon/talents) for a crit multiplier; dedicated crit flavor lines. Starting knobs: base crit ~5-10% at 1.5x (tunable per weapon).
4. **Raw damage.** `weaponYield * variance(+-~15%)` per projectile, * crit. Apply the family damage-type triangle multiplier (Section 3) and per-type resists (Section 5).
5. **Mitigation, in strict order:**
   - **a. Shield Attenuation split (PARTICLE weapons only):** a fraction (attacker `shieldAttenuation` minus defender `shieldCoherence`) skips shields straight to the hull-path. Particle weapons are never fully walled by shields. Kinetic and EW do NOT attenuate.
   - **b. Shields absorb** the rest up to the current shield pool; overflow continues to the hull-path. Shields regen `shieldRecharge`/sec, so drawn-out fights let shields tick back, rewarding burst.
   - **c. Armor** on the hull-path: `ablativeArmor` (depleting buffer that soaks first) then `kineticDampening` (% reduction). Kinetic weapons apply Armor Penetration (Section 3), ignoring a % of these.
   - **d. Hull** takes the remainder. Hull 0 -> enemy destroyed / your ship reaches the loss-retreat threshold.
6. **Effect procs.** On hit, roll the weapon's 2 effect slots (disruptions/DoTs) at rank 1, with escalation (Section 4).
7. **Durability.** A hit is a durability "damage event" for the target's systems (Section 9).
8. **Log** the event with the shield/hull result so the flavor matches reality.

## 3. Weapon families, the triangle, and the roster

**Three families, permanent.** Growth = new TYPES within a family, never new families unless something truly does not fit ("not Pokemon: Too Many Types"). Each family has a signature trait AND a modest damage-type triangle multiplier (a lever, not a hard counter).

**Damage-type triangle (+10% / 0% / -10%):**

| Family | vs Shields | vs Armor (Hull) | vs Drones | Signature trait |
|---|---|---|---|---|
| **Particle** | +10% | -10% | 0% | **Shield Attenuation** (partial hull damage through shields; steady pressure) |
| **Kinetic** | 0% | +10% | -10% | **Armor Penetration** (hard-walled by shields, but shreds armor/hull once they drop; the finisher) |
| **Electronic Warfare (EW)** | -10% | 0% | +10% | **Disruption-focused**, weak direct damage (poor vs hull, neutral vs shields); the support/debuff family. NOT the drone family (drones are a separate hangar system, Section 8), but EW carries the anti-drone tools. |

Loadout composition matters: EW cripples shields -> Kinetic shreds the exposed hull; Particle chips through shields the whole time.

**Weapon stats:** `weaponYield` (min-max range), `weaponAttackRate` (-> `secondsPerAttack`), `weaponAccuracy`, `weaponProjectileCount`, `range` (see range bands, Section 6). Family + type + **2 effect slots** complete a weapon. High-draw weapons cost power (Section 10).

**v1 roster, the nine (3 per family), built this patch:**
- **Particle:** Plasma, Graviton, Voltaic.
- **Kinetic:** Railgun, Autocannon, Concussion Torpedo.
- **EW:** Point-Defense Array, EMP Cannon, Tachyon Burst Emitter.

Locked identities carried from the prior doc (v1 subset): Plasma = strong Plasma Fire DoT; Voltaic = anti-shield, bonus shield damage + shield disruptions, chains across targets, NO attenuation (weak vs hull once shields drop); Railgun = high yield/accuracy, armor penetration + Targeting Drift; Autocannon = low yield/high rate sustained hull DPS; Concussion Torpedo = heavy warhead, high yield/low rate + Coolant Leak; Point-Defense Array = anti-drone/small-fast, does NOT hard-destroy torpedoes; EMP Cannon = drone damage + stun + power/system disruptions; Tachyon Burst = great vs drones + buffed vs shields (deliberate EW exception), sensor disruptions; Graviton = engine disruptions.

**Reflect/deflect is PARTICLE-ONLY** (Section 8): a torpedo or any kinetic that connects with a drone cannot be reflected.

**DEFERRED specialty weapons** (all of them, incl.): Neutron (anti-crew), Ion, Laser, Hyperon, Mass Driver + variants, Breaching Lance, Seeker Torpedo, Flak Cannon, Microwave Emitter, Signal Jammer, Proximity Cluster Mines, Viral Lance. Identities preserved in the prior doc + SUGGESTIONS.

**Install caps + class gates (forward hooks, wired in v1):** weapons carry `installCap` (top-tier weapons = max 1 mounted) and class restrictions as first-class fields; specific top-tier lockdowns are future balance content. Standard-Issue baseline: weapons are EXEMPT (a ship can fly unarmed); weapons + modules are singular per type (no 3-variety rule).

## 4. System Disruptions, DoTs, and the unified status-effect system

One generic **status-effect system**: a combatant carries a list of timed effects, each ticking each 0.1s step, each type-flavored and shown as a status pip. Three flavors of effect share the engine:
- **DoT effects** (e.g., Plasma Fire): deal damage every tick (likely straight to hull, internal). Log shows **one aggregated line per DoT per round**, not per tick. Rounds are delineated in the log (`-- Round N --`).
- **Debuff effects** (EW disruptions): degrade enemy systems (see table).
- **Buff effects** (module procs, support-drone buffs): shield surge, faster charge, etc.

**Ranks:** every proc applies rank 1 on hit; subsequent hits can escalate to rank 2/3/... (cap TBD); escalation chance scales with the weapon's quality + rarity. Higher rank = higher proc chance AND bigger effect (e.g., Plasma Fire I -> II). Refresh + tier-escalation stacking (reapplication extends duration and can escalate the tier), capped, no unbounded stacks. Rank 1 example magnitude ~20%.

**System Disruptions table (one shared pool):**

| System | Effect | Name |
|---|---|---|
| Sensors | -accuracy | Scattering Field |
| Sensors | -range | Sensor Power Drain |
| Engines | -maneuver | Manifold Overheat |
| Engines | -speed | Coolant Leak |
| Shields | +damage taken | Emitter Overload |
| Shields | +attenuation | Harmonic Gap |
| Shields | -recharge | Capacitor Failure |
| Weapons | -damage | (name pending: Power Sag / Emitter Fatigue / Coil Dampening) |
| Weapons | offline chance | Weapon Jam |
| Weapons | -accuracy | Targeting Drift |
| Drones | -attack rate | Inhibit |
| (DoT) | burning over time | Plasma Fire (+ future: irradiation, etc.) |

Each disruption/buff carries name + flavor + a mechanical effect line + a color. Weapons roll their 2 effect slots from this pool; modules/gear can add or change which a weapon inflicts. Builds split generalist (spread) vs specialist (stack one reliably). **Disruptions persist after a battle** and tick down over time.

## 5. Defense model

Resistances are DUAL-purpose: a resistance cuts both incoming DAMAGE of its type AND the chance + rank of that type's disruptions landing. Counter-building is real. Defense gear rolls two knobs per type: **damage resist** and **disruption resist**.

- **Shield lines:** `shieldCapacity`, `shieldRecharge`, `shieldAttenuation` %, `shieldCoherence` (attenuation resist), per-type shield resist.
- **Hull lines:** `hullStrength` / `hullIntegrity`, `ablativeArmor` (flat energy reduction, depleting buffer), `kineticDampening` (flat kinetic reduction), per-type hull resist.

(Stat keys `bleedthrough` / `bleedthroughResist` in the reserved vocabulary are renamed to `shieldAttenuation` / `shieldCoherence`; inert today so no migration.)

## 6. Targeting, range bands, movement, stance

**Range: continuous 1D distance crossing three BANDS (Long / Medium / Short).** Each weapon has a `range` (band); it fires only when the target is within it. Ships change distance with `movementSpeed`; `maneuverability` feeds evasion + closing agility.

**Stance** (player-set per ship, adjustable per dispatch, default Balanced): **Aggressive** (charge to short range; exposes you), **Balanced** (mid), **Standoff** (kite at long range). The sim moves each ship toward its stance's preferred range; enemies run their own stance from their loadout.

**Targeting:** per-combatant policy. Player default: **focus-fire the lowest effective-HP enemy in range.** Enemy policy: weighted pick, mostly your warship, with a tunable share to the escort (the "occasionally takes fire" knob). A weapon with no valid target in range holds while the ship closes.

**Encounter open** (default): long-range start -> "entered sensor range" -> "course set to intercept" -> "powering and preparing weapons" (weapons pre-charge during the close) -> the instant a weapon's band opens, its charged salvo fires (only the longest-range weapon in range fires the opener; shorter guns join as you close). Being out-ranged is punishing (enemy fires during your approach). A short-range brawler must survive the walk-in.

## 7. Openers: ambush, first strike, cloak

Symmetric (the player can land ambushes too: "Captain X caught the enemy unaware!").
- **Ambush:** a free opening salvo that strikes **hull directly** (the target is mid "raising shields and powering weapons", shields not up yet). The ambushed party's firing timer starts only AFTER that first hit lands.
- **Torpedoes are barred from ambush openers** (a hull-direct torpedo is a delete button). Limited to lighter/faster weapon classes.
- **Cloak** is a flavor of ambush: a cloaked enemy decloaks already in range and unloads before you react. Player-side cloaking stays deferred (heavy drawbacks TBD); for v1 cloak is a threat enemies bring.
- **Counters (Modules):** a **Combat-Reflex / Rapid-Charge** module shortens the post-ambush charge delay; a **Particle-Trace Detector** module gives you a chance to raise shields before the first hit (downgrading an ambush from hull-direct to a normal shielded opener).

## 8. Drones (full sub-system, v1)

Drones are offense/defense/utility stand-ins. Carriers live and die by them; no-EW vs a carrier is a bad day.

**Hangar Bays + Pods:**
- A **Drone Hangar** equippable fills the cargo-hold slot (slot flexes: 100% cargo / 100% drones [carrier-only] / 80-20 split; slot name may want a tweak, e.g. "Bay/Hold"). Carriers get **built-in hangar bays** plus the hangar system (~2 built-in + ~10 from the system, ~12), at the cost of **reduced weapon hardpoints**.
- A hangar grants **N bays**. Each bay holds **one Drone Squadron Pod** = one squadron of one type. Compose your screen by choosing types per bay (single-type per bay; mix across bays). Discrete bays => no wasted space.
- **Pods are equippable items**, swapped only when the captain is idle / ship parked (like all gear). Type-specific **Fabricators** build drones; type-specific **storage alcoves** hold spares; equip pods into generic bays. Mirrors the existing Fabricator -> Warehouse -> fit-to-ship pipeline (reuse).
- **Squadron size scales with hangar TIER** (baseline Attack 8 / Defense 10 / Support 6; ~+4 at top tier). Modules do NOT change count. Future set/legendary affixes may (`+squadron size`, `+bay`).
- **Drone brand/model names** are unique per drone (content, like the weapon roster), not placeholders.

**Three roles, three auto-assigned modes (no toggle):** Attack -> Mode 1 (attack/kill), Defense -> Mode 2 (defend/retaliate), Support -> Mode 3 (support). All drones have HP.

**The three interaction cases (this IS the drone AI):**

| | **Attack** | **Defense** | **Support** |
|---|---|---|---|
| **Squadron attacks** | Zoom in, fast sweeping strikes, shred | Hang by carrier, long-range, slow, few projectiles, low dmg | Like Defense but even lower dmg/speed; mostly utility |
| **Squadron is targeted** | Try to evade; hit = damaged/destroyed if HP penetrated, evade = fine | Low evade; absorb/block; **deflect/reflect/smart-reflect** (particle-only); destroyed only if hull+shield penetrated | Evade like Attack |
| **Carrier is targeted** | Can intercept: LOWER evade than self-defense but a **solid counterattack** on success; else eat it, die if penetrated | Intercept: HIGHER deflect than self-defense (not counterattacking) -> deflect harmlessly / reflect at attacker / smart-reflect at a weaker enemy; else absorb with HP, overflow to carrier | Pure meat-shield: no evade/deflect; takes the hit, weapon punches through for `damage - drone remaining HP` onto the carrier |

- **Reflect / smart-reflect is PARTICLE-ONLY** and can be added/upgraded by modules; a carrier-exclusive **smart-reflect** picks a target by priority (Support-first, etc.). Torpedoes/kinetic that connect cannot be reflected.
- **Multi-hit projectiles vs the screen:** an attack with N projectiles pulls up to N drones into defending, so squadron size = defensive throughput and high-projectile weapons **saturate the screen** (leak through a thin screen).
- **Individual-unit tracking** (cheap at 6-10/squadron): each drone has HP + status. Per-drone status pips (small squares + tooltips): 🟢 **Online**, 🟡 **Disrupted** (repairing 0-100%; disruptions persist post-battle), 🔴 **Refabricating** (0-100%).
- **Support kit (Mode 3):** small **hull repair per tick** to carrier/allies, no offense, **disruption cleanse whose chance halves per rank** (rank1 base%, rank2 half, rank3 quarter). Essential in fleet ops, weak solo.
- **Balance:** a squadron is tuned to be roughly as potent as the equivalent weapon load it replaces (default squadron ~= one equivalent weapon, spread across the drones).
- **Replenishment:** an implicit `droneReplenishRate` rebuilds destroyed drones **only out of combat** (which includes traveling between waves, so a screen recovers between waves like shields do; fast waves = incomplete recovery). A **module** unlocks `x%` of that rate DURING combat for a sticky-screen build.

## 9. Durability (v1)

Gear loses durability on **damage events** (a hit is an event). Quality mitigates: higher quality = ~+100% durability and -10%/rank chance to lose a durability point per event. Worn gear is repaired at the Shipyard (folds into the repair-bay loop, Section 13). Ship-system condition surfaces as a status pip (Section 16): 🟩 Nominal / 🟨 Degraded (low durability, reduced effectiveness) / 🟧 Disrupted (active disruption) / 🟥 Offline (durability depleted or hard-disabled, e.g. Weapon Jam).

---

## 10. Power / reactor budget (v1)

Reactor `powerOutput` vs total loadout `powerDraw` gates what you can fit. You cannot stack the craziest weapons/modules if the reactor cannot supply them. Makes loadout a real tradeoff (`reactorTier` also gates equip/module tiers, forward).

## 11. Combat rating: Battle Rating + Engagement Forecast

Two numbers (solves the "25,000 loses to 3,000" problem):
- **Battle Rating:** a stable, opponent-agnostic scalar composite of your combat stats. Your "how geared am I" number.
- **Engagement Forecast (%):** shown at mission-select vs a SPECIFIC enemy; runs your build vs theirs through the real matchup (elements, resists, disruptions, range) to predict success honestly.

Both are **advisory** (the fight is a seeded sim; you can dispatch under-geared and still win, or lose a favored fight). Rating is derived, not earned.

## 12. Rewards and loot

Reuse existing systems. All rolls seeded.
- **Wreck salvage:** salvaged materials (existing `salvagedMaterial` category) + a guaranteed **"Damaged [System]"** reverse-engineering component (reuses the Damaged Reactor Housing idiom; e.g. a Damaged EMP Cannon salvages into part of its recipe).
- **Cargo-hold contents:** a small roll, ~1-2 salvage + a mix of raw / refined / component.
- **NO functional gear** drops from wrecks (protects the crafting loop; combat FEEDS crafting, does not bypass it).
- **Credit bounty.**
- **Captain XP + FA XP** (rides existing tracks; no standalone combat level).
- **Rare collectible** (trophy/commendation class): reserve the hook only; mechanics designed later.
- All wreck loot modeled as **tables** so ship-class-specific + rare-enemy bounty tables slot in later.

**Progression:** combat rides captain XP + the **spec talent trees** (RadialWeb). Tactician = combat-primary (damage/accuracy/crit/shield tuning); Explorer = evasion/first-strike/detection; Prospector = salvage yield/extra cargo rolls; an **infamy** talent raises a patrol's max waves (more risk/reward). No fourth XP bar. Weapon proficiency + captain proficiency (a permanent one-time locked pick per spec) are DEFERRED.

## 13. Loss / repair loop + Shipyard bays

No destruction in v1 (permadeath deferred). Loss = "restore systems, retreat":
- Limp home at **2x return time** (movement damaged; a crew bonus/module can grant exceptions, hook only).
- Auto-route to the Shipyard; the ship **cannot be re-dispatched until repaired**; repair is a timed process scaled by damage taken. **Hull does not regen between waves** by default (only shields do, per tick during transit).
- **Shipyard Bays** are shared build/repair (and future refit). Rule: **at least one bay is always reserved so a build cannot occupy it** (you can always repair >= 1 ship); idle build capacity flexes into repair. Damaged ships with no open bay sit in a **"waiting for repair"** queue.
- Reservation is **repair-favored only** (builds use all-but-one; repairs use any free bay). Configurable build/repair allocation is DEFERRED (v1 is automatic). Refit is DEFERRED (bay modeled role-agnostic so it drops in).

## 14. Mission integration: the Patrol loop

Combat lives ONLY in combat missions in v1 (Patrol first; Escort is a fast-follow; combat-chance bleeding into other mission types is future). "All missions can have combat" is the north star, not the first shipment.

- **Dispatch** from Operations: a **Patrol** card, assign captain + ship, pick stance, pay fuel, launch. **Dispatch Once / Dispatch Repeatedly** toggle (run-once for risky patrols vs auto-repeat).
- **Multi-wave.** The card shows **Combat Waves: min-max** (min = guaranteed, max = ceiling / "chance points"). Route example (100 ticks, waves 2-4): ticks 0-10 initial transit (no rolls, shields regen); at tick 10 the patrol begins and you **roll every tick**; guaranteed minimums are enforced via spread "catch-up" checkpoints (min 2 -> latest triggers ~tick 20 and ~tick 90; more mins spread evenly); successful rolls add waves up to max; once `max` waves are fought, rolls stop. Always >= min, never > max. **Infamy talents raise max.** The actual wave count is revealed wave by wave.
- **Enemies** use the same stat model as you (hull/shields/weapons/stance), generated **deterministically** (seeded). Each starting Patrol is tied to a **named pirate faction** (a lightweight `Faction` data record: id + name + flavor; reputation scalar + consequences DEFERRED but the seam is live). Enemies may bring drones (so anti-drone weapons matter and EW is complete).
- **Between waves** you travel the route: shields regen per tick, drones replenish per `droneReplenishRate`, hull persists (attrition survival test).

## 15. Captain Identity (Phase 1 prerequisite)

Combat depends on this, so it lands FIRST.
- **Captain id -> monotonic counter** (`nextCaptainId`, never reused), like ships/equipment. Fixes the current length-derived scheme (SUGGESTIONS line 598) so combat's stable references + custom names attach to a stable identity, and future captain death/turnover never recycles ids.
- **Custom naming.** The reserved Rename panel goes live (default stays "Captain N"). Real captain names make the combat log land ("Ravenscar caught them unaware!").
- **Validation seam.** One chokepoint `validateCaptainName()`: light in-house validation now (length, charset, trim, safe-to-render) + a **small in-house PROFANITY blocklist** (no external dependency, minimal attack surface). Violence + nuance are hand-moderated later. Real moderation is server-side, plugging into the SAME chokepoint in the 0.14.0 online/admin work (force-rename, temp bans, account suspensions w/ 3-request/1-week-cooldown unbans).

## 16. Combat modes + Combat UI

**Two modes, both v1** (same event stream underneath):
- **Log-Guided (default):** scrolling round-by-round text with `-- Round N --` dividers, flavored lines, one aggregated DoT line per round; streams ~1 round/sec live.
- **Visual:** damage numbers pop over the ship icons, styled per weapon family/type.

**Flavor system (data-driven).** Every event is a structured record `{ t, type, actor, target, weaponFamily/type/signature, damage, result, crit?, shieldHullSnapshot, disruptionType? }`. Flavor is a **layered pool with most-specific-wins fallback**: signature-weapon -> weapon-type -> weapon-family -> generic, per event type. Author type/signature spice only where it adds identity; inherit family lines otherwise (viable, no combinatorial explosion). Dedicated pools per event type (shield hit, hull hit, shield-break, evade, crit, attenuation, armor-pen, disruption, ambush, destruction, retreat). Flavor picks use the **cosmetic** RNG stream. Names/numbers interpolate.

**Combat view elements** (shared surface): ship portraits (your paper-doll facing the enemy; enemy composition; escort later); live hull + shield bars; **small square status pips + tooltips** for disruptions/DoTs/buffs; per-drone squadron pip rows (Online/Disrupted/Refabricating); ship-system condition pips (Nominal/Degraded/Disrupted/Offline); range readout with Long/Med/Short band markers + weapon-range indicators for both sides; phase narration (detection -> intercept -> weapons-ready -> firing); mode toggle.

**Where it lives:** under **Operations**. Dispatch a Patrol; while it runs you can **open the combat view to watch live**; if away, it resolves headless and lands in the While-You-Were-Away summary (Section 17). The reserved Battlespace tabs remain the future home of the 2.0 interactive turn-based mode.

**Process:** the spatial LAYOUT is **mockup-gated**, an HTML mockup for sign-off BEFORE any combat-UI code, per the standing rule.

## 17. Offline overhaul + determinism + save version

- **Offline combat = same deterministic math, no theater.** Same seed -> identical outcome to live, but skips log/flavor generation (pure outcome + reward calc). Seeded, so a battle's log COULD be regenerated on demand later ("replay while away"); v1 offline is results-only.
- **While-You-Were-Away overhaul.** Today's welcome-back barely reports anything. Combat needs a real report: patrols resolved, waves won/lost, loot + bounty banked, ships that limped home into the repair queue, captain statuses. Its own workstream in the patch.
- **Seed derivation.** Each encounter's seed derives deterministically from a persisted master seed + the encounter's position, so live and offline produce the same fight. Master seed persists in the save.
- **SAVE_VERSION bump + forward-migration.** Combat adds substantial persisted state (weapons/modules/drones/pods, durability, repair queue + bays, damaged/limping ships, captain counter + names, faction data, per-mission combat config). `SAVE_VERSION` bumps with a migration that backfills existing saves (captains -> counter ids, default names, full durability, empty repair queue, etc.). **Existing saves carry forward, NOT nuked.** The server-side save-nuke/version-gate is a separate later (balance/online) concern.

## 18. Testing

Headless determinism makes this highly testable (vitest + characterization snapshots, the codebase's existing style):
- **Flagship parity:** same seed -> identical outcome each run; **offline (no log) == live (with log)** outcome; **cosmetic-stream isolation** (adding/editing flavor never changes an outcome).
- **Bounded termination:** tank-vs-tank hits the round cap and tiebreaks.
- **Mechanic units:** shot pipeline + mitigation order (shields -> attenuation -> armor -> hull); DoT tick + rank escalation + per-round aggregation; disruptions (apply/tick/cleanse, half-per-rank); all drone interactions (evade/deflect/reflect/smart-reflect particle-only, meat-shield overflow, multi-projectile screen saturation); power-budget gating; durability loss; family triangle; range-band gating.
- **Wave model:** always >= min via checkpoints, <= max, infamy raises max, deterministic count.
- **Repair loop:** limp-home 2x, bay contention + queue + the always-reserved repair slot.
- **Loot + Battle Rating (monotonic w/ gear) + Engagement Forecast sanity.**
- **Migration:** existing saves upgrade cleanly (extend `save.test.ts`).
- **Offline catch-up integration:** long absence with active patrols -> correct outcomes/rewards/repair queue, matching live.
