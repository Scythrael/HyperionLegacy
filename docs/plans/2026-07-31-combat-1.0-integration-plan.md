# Combat 1.0 Integration Plan (phased)

> **For Claude:** The implementation plan for `2026-07-31-combat-1.0-integration-design.md`. Built the same way as the 0.13.0 engine: subagent-driven-development (implementer + spec review + code-quality review per unit), branch-direct commits on `feat/combat-0.13.0`, gate GREEN each unit (check + full suite + the 100-test parity fuzz `-t "parit"`). Phase 1 is detailed into ordered units below; Phase 2 is outlined and expanded just-in-time when Phase 1 closes. Modules are Combat 1.1 (out of this plan). This doc carries the build across sessions.

**Definition of done (Combat 1.0):** a ship with an empty required combat slot cannot patrol; weapons, shield emitters, hull plating, and drone pods are craftable, implicit-rolled items that drive real combat outcomes; every defensive stat is fed by gear; 12 of 13 status effects are live and honest; enemies scale to keep patrols winnable; HELP + patch notes updated; a curated QA sheet passes on desktop + mobile; one clean 0.12.1 to combat-1.0 prod migration. Offline == live holds at every step.

**Standing gates (every unit):** `npm run check` 0 errors, full `npx vitest run` green (baseline 1614, grows as units add tests), and `npx vitest run -t "parit"` green. Any unit that changes a combat OUTCOME re-baselines the parity fixtures deliberately and proves offline == live with the new inputs. HELP + patch notes updated per the piece that landed (standing definition-of-done from 0.13.0).

**Anti-regression:** the extraction mission arm, the economy tick, and save load stay byte-identical unless a unit's scope explicitly changes them (Omega 15). Combat gear reuses the existing `EquipmentInstance` storage, itemgen budget engine, and Fabricator to Warehouse to install pipeline; we extend, we do not fork them.

## Phase 1: Gear-driven combat

Ordered so the model/data plumbing lands first (parity untouched, combat still runs on hull defaults), the outcome-changing bridge wiring lands as one deliberate re-baseline in the middle, and content + UI + rebalance close it out.

### Unit 1.1 — Combat slot types + shield & plating slot defs + Standard-Issue baselines (data only, parity untouched)

- Add `shieldEmitter` and `hullPlating` to `EquipmentSlotType` (model.ts). They store as normal `EquipmentInstance`s (fittedToShipId + slotType) in `state.equipment`; no new collection.
- Add their `EQUIPMENT_SLOTS` entries: `shieldEmitter` implicits `shieldCapacity` + `shieldRecharge`, affixes `shieldCoherence` + per-family shield resist; `hullPlating` implicit `hullStrength`, affixes `ablativeArmor` + `kineticDampening` + per-family hull resist. Add the new stat keys to the shared allow-set the itemgen test fences.
- Author the Standard-Issue baseline items for both slots (quality 0, neutral rolls, weak), mirroring the 0.11.0 Standard-Issue precedent.
- NO bridge change (shipToCombatant still reads hull stats). This unit is pure data + storage plumbing.
- **Gate:** check + suite + parity all green and UNCHANGED (combat outcomes must not move yet).

### Unit 1.2 — Weapons as craftable, rolled items

- Add `weapon` slot type (multi, hull hardpoint count). Keep the nine `WEAPON_DEFS` as authored BASE types (family, triangle, signature, base range/projectiles, effect-slot identity).
- Convert `makeWeaponInstance` from a flat template clone into an itemgen mint that produces an `EquipmentInstance` whose quality/rarity/iLevel roll `weaponYield`, `weaponAccuracy`, durability ceiling, crit, and effect-slot proc/escalation (reuse `itemgen.ts` budget-share + affix mechanism).
- Weapons enter the craft chain: research blueprint (reuse the unlock-only blueprint idiom or an equipment-output blueprint per recipe) then Fabricator mints them; Standard-Issue weapon baseline authored per combat hull.
- Activate `installCap` (top-tier caps at 1 mounted) and weapon class-restriction gates at install time.
- May sub-split (1.2a base-type-to-itemgen + roll; 1.2b craft chain + blueprints + Standard-Issue) if the diff is large.
- **Gate:** check + suite + parity green; combat still runs on hull defaults (weapons exist as items but the bridge does not read them yet), so outcomes still must not move.

### Unit 1.3 — Auto-install baselines on build + migration; the dispatch blocker

- On ship build and on save migration, fill every combat hull's required slots {>=1 weapon, shieldEmitter, hullPlating} with the Standard-Issue baselines, so no ship is ever bricked.
- `canDispatchPatrol` (tick.ts) returns a clear reason when a required slot is empty ("No weapon installed" / "No hull plating installed" / "No shield emitter installed"). Combat hulls now REQUIRE a weapon to patrol (overrides the 0.13.0 fly-unarmed exemption for combat hulls only).
- `SAVE_VERSION` bump + migration (auto-install on load of a pre-gear save). Per-phase bump, devpreview only.
- **Gate:** check + suite + parity green; migration idempotent + version canaries bumped; extraction + existing patrol dispatch still work.

### Unit 1.4 — Bridge wiring: shipToCombatant reads fitted gear (the payoff, PARITY RE-BASELINE)

- `shipToCombatant` (bridge.ts:314-335) stops hardcoding: hull <- frame + `hullPlating.hullStrength`; shield <- `shieldEmitter.shieldCapacity`; shieldRecharge, shieldCoherence, ablativeArmor, kineticDampening, damageResist, disruptionResist, evasion, speed all <- their gear/hull-stat sources per design Section 7. Weapons <- the ship's fitted weapons (fall back to the Standard-Issue baseline; `COMBAT_DEFAULT_LOADOUT` becomes the baseline definition).
- **This unit changes combat OUTCOMES on purpose.** The parity fixtures are re-baselined against gear-driven inputs, and offline == live is re-proven with the new inputs (this is the single deliberate outcome shift of Phase 1; it is isolated here so the re-baseline is one reviewable event, not smeared across units).
- **Gate:** check + suite green; parity fuzz green with the NEW gear-driven fixtures; a test proving a geared ship and a Standard-Issue ship produce different, correct outcomes; enemies still beatable enough to test (full rebalance is 1.6).

### Unit 1.5 — Status effect completion (the five Phase 1 effects)

- Wire the READERS for Emitter Overload (`damageTaken` multiplier in `applyProjectileDamage`) and Weapon Jam (`weaponOffline` checked in the firing gate). These proc live today but do nothing; this is close to a correctness fix.
- Give Sensor Power Drain, Coil Dampening (name the pending effect), and Harmonic Gap a weapon SOURCE via Unit 1.2's effect-slot rolls; wire Harmonic Gap's `attenuation` delta into the mitigation split.
- Reach 11 of 13 effects live (Inhibit waits for Phase 2 drones; Overcharged Capacitors buff waits for 1.1 modules).
- **Gate:** check + suite + parity green; a test per newly-live effect proving it changes an outcome.

### Unit 1.6 — Enemy stat model (hybrid) + rebalance #1

- Implement the DECIDED hybrid: authored enemy loadout TEMPLATES (real weapon defs + a stat budget authored as a fraction of an equivalent player fit) in `enemyHulls.ts`, scaled by a single per-tier difficulty scalar threaded through the reserved `enemyWave.ts` params seam (T-I..T-X forward hook).
- Rebalance pass #1: retune the starter patrol + durability so all three tactician hulls with Standard-Issue gear can win, and better gear meaningfully improves the odds. Reuse the `patrol-balance.test.ts` harness (drives real economyTick).
- **Gate:** check + suite + parity green; balance test locks the starter winnable by Standard-Issue-geared hulls.

### Unit 1.7 — Weapon-crafting loot ("Damaged [System]" drops)

- Fill the reserved `damagedSystem` slot in `patrolLoot.ts` now that weapon/gear crafting exists: wrecks drop a `Damaged [Weapon/Shield/Plating]` that salvages into build materials (reuse the Damaged Reactor Housing idiom). No functional gear drops.
- **Gate:** check + suite + parity green; win-only, seeded, no-functional-gear invariant test.

### Unit 1.8 — ShipSystemsPanel combat slots UI (MOCKUP-GATED)

- HARD GATE: build an HTML mockup of the combat-fit screen (weapon hardpoints, shield, plating slots; install/uninstall; the dispatch-blocker messaging) and get user sign-off BEFORE any Svelte code (per the visual-UI-needs-a-mockup rule). Use INSTALL/INSTALLATION terminology, never fit.
- Then build the panel: combat slots alongside the existing four, reuse EquipmentTooltip (its implicit/affix bands already exist; its design is a hard-constraint preserve), install/uninstall in one tap, live stat changes.
- **Gate:** mockup approved; check + suite green; local visual pass caveat (preview misroots for this repo, user does the device pass).

### Unit 1.9 — Phase 1 close: HELP + patch notes + QA sheet + parity + review

- HELP topics refreshed for combat gear (weapons/shields/plating as items, install, the dispatch blocker). Patch notes drafted. Holistic review of Phase 1 vs the design doc.
- Curated desktop + mobile QA sheet (per the standing QA-sheet process) for the user to run on devpreview.
- **Gate:** everything green; QA sheet delivered.

## Phase 2: Drone content + readouts (outline, expand JIT)

- **2.1 Drone pods as items:** `DronePod` becomes a craftable `EquipmentInstance` with a `droneBay` slot type + bay index; type-specific fabrication lines + Warehouse storage; install to a bay while parked. Reuse the fit pipeline.
- **2.2 Hangar bays as real capacity:** `builtInBays` gates squadron count; carrier built-in bays + optional hangar-system bays; non-carriers 0. Wire hangar-tier squadron scaling (callers stop passing tier 0).
- **2.3 Dormant behaviors go live:** defense + support squadrons reach the field (deflect, particle reflect, flip `smartReflect`, meat-shield overflow, support hull-repair pulse + cleanse). No new sim code, just real loadouts. Wire Inhibit (12 of 13 effects).
- **2.4 Battle Rating + Engagement Forecast UI (MOCKUP-GATED):** surface the built `rating.ts` functions on ship cards + the Patrol dispatch card. Advisory. (Threat-Assessment band design already captured in the 0.13.0 memory; reconcile at expansion.)
- **2.5 Rebalance #2 (carriers) + Phase 2 close:** retune with drone screens in play; HELP + patch notes + QA sheet.
- **Debut:** one complete prod promotion after Phase 2; single clean 0.12.1 to combat-1.0 migration; explicit user go after QA passes.
