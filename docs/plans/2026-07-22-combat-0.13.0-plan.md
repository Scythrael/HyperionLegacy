> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (or executing-plans) to implement this plan phase-by-phase, task-by-task. This is a LARGE epic. **Phase 1 is detailed to executable tasks now; Phases 2 to 14 are outlined at task level and MUST be expanded to bite-sized TDD tasks just-in-time at the start of each phase** (re-read the relevant design-doc section + the real code, then write that phase's tasks). Expanding all 14 phases up front would be thousands of lines and would drift against code that does not exist yet.

**Goal:** Ship feature-complete Combat 0.13.0 per `docs/plans/2026-07-22-combat-0.13.0-design.md`.

**Architecture:** A pure, deterministic, seeded, headless `resolveBattle(participants, seed) -> { outcome, log }` fixed-timestep simulator (integer math, two RNG streams), plugged into Patrol combat missions, with weapons/families/disruptions, drones, durability, power budget, repair-bay loop, combat UI, and an offline overhaul. Offline == live is a hard invariant.

**Tech Stack:** Vite + Svelte 5 legacy `$:` reactivity, TypeScript, `src/lib/game/{model,tick,save,itemgen,salvage}.ts`, `src/App.svelte`, vitest.

**Branch:** `feat/combat-0.13.0` (design + this plan already committed here).

**Conventions (do not violate):** No em dashes / no "--" (CSS `var(--x)` exempt). Integer/fixed-point sim math. Two RNG streams (combat vs cosmetic). TDD, frequent commits, `npm run check` + `npm test` green before each commit. Every state-adding phase bumps `SAVE_VERSION` + adds a backfill migration (existing saves load, never nuked). Spatial UI (combat view) is MOCKUP-GATED: build an HTML mockup for user sign-off BEFORE any combat-UI code. Update HELP + patch notes as part of done.

## PHASE 1: Captain Identity (detailed, executable)

**Why first:** combat holds stable captain references and attaches custom names to identity; the current id scheme is length-derived and would collide on removal (future captain death). Fix now.

**Reference:** design doc S15. Mirror the existing `nextShipId` (model.ts:2226) / `nextEquipmentId` (model.ts:2303) monotonic-counter pattern. Captain ids are NUMBERS (stay numbers; allocate from a counter instead of `length + 1`).

### Task 1.1: Add `nextCaptainId` to GameState + seed in freshState

**Files:**
- Modify: `src/lib/game/model.ts` (GameState interface near line 2226-2303; freshState near line 4700-4760; `freshCaptains` at 4622-4633)
- Test: `src/lib/game/model.test.ts`

**Step 1 (test, fails):** Add a test asserting `freshState().nextCaptainId === 2` (one starter captain "Captain 1" uses id 1, so the next is 2), and that `freshCaptains(3)` still yields ids `[1,2,3]`.

**Step 2:** Run `npx vitest run src/lib/game/model.test.ts -t "nextCaptainId"` -> FAIL (property missing).

**Step 3 (implement):** Add `nextCaptainId: number;` to `GameState` (beside `nextShipId`), with a comment mirroring nextShipId's ("monotonic id source for new CaptainState.id; never reused"). Seed `nextCaptainId: 2` in `freshState()` (one starter captain). Leave `freshCaptains` as-is for the initial deterministic 1..count seeding (it only runs at genesis/migration).

**Step 4:** Run the test -> PASS. Run full `npm run check` (a new required field will surface every GameState literal that must set it, e.g. test fixtures; fix them to `nextCaptainId: <max captain id + 1>`).

**Step 5:** Commit `feat(combat): add nextCaptainId monotonic counter to GameState`.

### Task 1.2: Allocate captain ids from the counter on slot-unlock

**Files:**
- Modify: `src/lib/game/tick.ts` (unlockCaptainSlot at 5039-5050, currently `const nextId = state.captains.length + 1;`)
- Test: `src/lib/game/tick.test.ts` (or model.test.ts if slot-unlock is tested there)

**Step 1 (test, fails):** Construct a state with captains `[{id:1},{id:3}]` (a gap, simulating a future removal) and `nextCaptainId: 4`; buy a captain slot; assert the new captain's `id === 4` and `nextCaptainId === 5` (NOT `captains.length + 1 === 3`, which would collide with the existing id 3).

**Step 2:** Run -> FAIL (gets id 3, collides).

**Step 3 (implement):** In `unlockCaptainSlot`, replace `const nextId = state.captains.length + 1;` with `const nextId = state.nextCaptainId;`, push `{ id: nextId, label: \`Captain ${nextId}\`, ...freshCaptainStack() }`, and set `nextCaptainId: nextId + 1` in the returned state.

**Step 4:** Run -> PASS. `npm test` green.

**Step 5:** Commit `fix(combat): allocate captain ids from nextCaptainId, not array length`.

### Task 1.3: Save migration v30 -> v31 (backfill nextCaptainId)

- Test: `src/lib/game/save.test.ts`

**Step 4:** Run -> PASS. `npm test` green (migration chain tests).

**Step 5:** Commit `feat(combat): SAVE_VERSION 31, backfill nextCaptainId on old saves`.

### Task 1.4: `validateCaptainName` seam (validation + in-house profanity blocklist)

- Test: `src/lib/game/captainName.test.ts`

## PHASE 2 to 14 (outline; expand each to bite-sized tasks at its start)

> For each phase below: at its start, re-read the cited design section + the real code it touches, then write that phase's Task N.x list in the Phase 1 style (files/test/steps/commit), and run it through subagent-driven-development.

### PHASE 2: Sim core skeleton (design S1) — new module `src/lib/game/combat/`
- `combat/rng.ts`: two seeded PRNG streams (`combat`, `cosmetic`) from a seed; deterministic, integer-friendly (mulberry32/xorshift). Test: same seed -> same sequence; streams independent.
- `combat/types.ts`: `Combatant` (id, team, hull, shields, position, weapons[], effects[], drones[]...), `BattleParticipants`, `BattleOutcome`, `CombatEvent` (structured log record per S16), `BattleObjective`.
- `combat/resolveBattle.ts`: fixed-0.1s-timestep loop shell (move -> weapons -> effects -> deaths -> objective), deterministic combatant order, round cap + tiebreak, emits `{ outcome, log }`. Stub the shot resolution (Phase 3 fills it). Test: a trivial 1v1 with a placeholder weapon terminates, is deterministic, and offline(no-log)==live(with-log) outcome.
- Establish the offline==live + cosmetic-isolation parity tests here as the flagship suite.

### PHASE 3: Weapons + families + shot pipeline (design S2, S3)
- Weapon data model (`weaponYield` min-max, `weaponAttackRate`->`secondsPerAttack`, accuracy, projectileCount, range, family, 2 effect slots, installCap/class hooks). The 9-weapon roster with locked identities.
- Cooldown accumulator with carry-over. Shot pipeline: accuracy vs evasion, projectiles, crit, damage variance, family triangle multiplier, mitigation order shields -> attenuation(particle-only) -> ablativeArmor -> kineticDampening -> hull. Fill resolveBattle's shot step.
- Tests: mitigation order + attenuation-particle-only + armor-pen-kinetic + triangle + carry-over fire timing (2.15/sec exact over N seconds) + crit/projectile independence.

### PHASE 4: Status effects: disruptions + DoTs + ranks (design S4)
- Unified `StatusEffect` (DoT | debuff | buff), timed, ticks per step. The System Disruptions shared pool (table). Rank 1 on hit, escalate to 2/3 (Plasma Fire I->II), refresh + tier cap, chance scales with quality+rarity. DoT damage per tick; log aggregates 1 line per DoT per round; rounds delineated. Disruptions persist post-battle (carry on the ship/gear).
- Wire the 2 effect slots per weapon to roll from the pool. Tests: apply/tick/expire, rank escalation, DoT per-round aggregation, cleanse half-per-rank (used by support drones later).

### PHASE 5: Defense + per-type resists + durability + power (design S5, S9, S10)
- Rename reserved stats `bleedthrough`/`bleedthroughResist` -> `shieldAttenuation`/`shieldCoherence` (inert, no migration). Per-type damage-resist + disruption-resist application (dual-purpose). Wire shieldCapacity/recharge, ablativeArmor, kineticDampening into the pipeline.
- Durability: a hit is a damage event; quality-scaled loss chance; deplete -> Offline condition. Ship-system condition state derivation (Nominal/Degraded/Disrupted/Offline).
- Power budget: reactor `powerOutput` vs summed loadout `powerDraw`; block over-budget fits (fit-time gate, like canFitEquipment). Tests each.

### PHASE 6: Positional + openers (design S6, S7)
- 1D distance + Long/Med/Short bands; stance (Aggressive/Balanced/Standoff) movement toward preferred range; focus-fire-lowest-HP targeting + enemy weighted pick (escort share hook). Encounter open (long-range, pre-charge, longest-range weapon opener). Ambush (symmetric, hull-direct, delayed return fire, torpedoes barred); enemy cloak as an ambush source; Rapid-Charge + Particle-Trace-Detector modules. Tests: band gating, stance movement, ambush hull-direct + delayed timer, torpedo-ambush-barred.

### PHASE 7: Drones (design S8) — the big one, sub-phased
- 7a: drone data model (roles Attack/Defense/Support, HP, evade/deflect, spaceless bay model), Drone Squadron Pod as an equippable, hangar bay slot (cargo-slot flex + carrier built-in bays), type-specific fabricators + storage alcoves (reuse itemgen/fabricator/warehouse). Squadron size by hangar tier.
- 7b: drone AI = the 3 interaction cases per role (squadron attacks / squadron targeted / carrier targeted), individual-unit tracking, meat-shield overflow, deflect/reflect/smart-reflect (PARTICLE-ONLY), multi-projectile screen saturation (N projectiles pull N defenders).
- 7c: replenishment (out-of-combat incl. between-waves via `droneReplenishRate`; in-combat module %). Carrier hull class (built-in bays + reduced hardpoints).
- Tests: each interaction case, reflect-particle-only, meat-shield math, screen saturation, replenishment timing.

### PHASE 8: Combat rating (design S11)
- Battle Rating (stable scalar composite) + Engagement Forecast (% via running your build vs a specific enemy through the matchup). Advisory. Tests: rating monotonic with gear; forecast sane vs known matchups.

### PHASE 9: Missions: Patrol + multi-wave + factions (design S14)
