# Ships Tab Redesign (0.13.2) — Design

- **Date:** 2026-09-01
- **Branch:** `feat/ships-tab-0.13.2` (off prod `892da75`)
- **Status:** design LOCKED (mockup v2 approved by user; artifact cb4befba). Grounded in the 2026-09-01 code map.
- **Save impact:** none expected. `activeTab` is not persisted; favorites live in localStorage. NO SAVE_VERSION bump (verify at close).
- **Parity:** pure UI/model. `npx vitest run -t "parit"` must stay exactly 101 throughout.

---

## 1. Why

Two problems, one release:

1. **The live tooltip-vanish bug.** Install/Uninstall actions are injected into a *floating* `EquipmentTooltip` (`ShipSystemsPanel.svelte:1213-1239`). On mobile and when zoomed, the tooltip re-positions or dismisses as the player reaches for the button, so the action target moves out from under the finger. Root cause, not symptom: **actions must never live in a hover/float surface.**
2. **Ships don't scale.** Ship management is buried as a Logistics sub-tab, and neither the roster nor the equip panel is built for 50+ hulls or hulls with 7+ weapon hardpoints.

The fix: promote Ships to a first-class destination, and make **tooltips display-only, every action a stable button**. This is a global principle from here on, not a one-off.

## 2. Scope

**In:**
- A 6th bottom-nav tab, **Ships**, with SVG nav icons and an attention dot.
- Move ship management **out of** the Logistics perspective into the Ships tab.
- Roster: sortable (attention-first default), favorites, class grouping, search, filter chips, a `damaged` indicator.
- Equip view = **Layout C loadout board**: hull identity tile + category-grouped slots; Offense = an **auto-scaling weapon-tile grid**; Defense/Systems = rows.
- Reworked **install flow**: INSTALLED banner + compatible-spare tile list + a platform-adaptive compare (desktop both-cards-in-one-pane, mobile drill), Install/Back/Cancel on stable buttons.
- **Display-only tooltips** (reuse `EquipmentTooltip` unchanged; stop passing its action slot).

**Out (explicit non-goals):**
- The standardized 6-template/1-payload **tooltip system** epic — deferred to its own later release (user 2026-09-01: "don't go too deep into tooltips, reuse what exists"). 0.13.2 only makes the existing tooltip display-only.
- Crafting overhaul (0.13.3), loadout presets (later), auto-salvage.
- Any economy or combat-sim change. No new gameplay.

## 5. State / data changes

- `TabKey` gains `"ships"`; `activeTab` unchanged mechanism (not persisted).
- Rename `logisticsShipsView` → `shipsView`, keep `selectedShipId`; move them + the vanished-hull guard out of the Logistics section. Remove `"ships"` from `activeLogisticsTab` + `LOGISTICS_TABS`; Logistics still defaults to `"materials"`.
- New UI state (plain, non-persisted): roster `sortKey`, `filterKey`, `searchText`; install-flow state (`installSlot`, `installCandidateId`).
- **Favorites** = a localStorage set of ship ids (per-device preference, mirroring `salvageConfirmPreference`). Wrapped in try/catch, renders correctly when absent. NOT in the save (so no schema change). Keyed by `ship.id` (stable within a save).

## 6. The simulate-candidate helper (load-bearing)

There is no "stats if X were installed" function, so the compare view builds a **hypothetical gear array** and re-runs the *same pure functions the real fold uses* (never a re-derivation):

```
currentGear = equippedFor(state, shipId)
candidateGear = applyHypotheticalInstall(currentGear, candidate, slot)
  // singleton slot: replace fittedInSlot occupant with candidate
  // weapon/droneBay MULTI slot: replace the targeted hardpoint, or fill the empty one
current  = readout(currentGear);   candidate = readout(candidateGear)
where readout(gear) = { rating: battleRating(shipToCombatant({...installedGear:gear})),
                        combat: computeCombatReadout(gear, stats, hardpointCap, droneBayCap) }
diff = per-stat (candidate - current), net = candidate.rating - current.rating
```

Implement as a **pure, node-testable helper** (new `src/lib/game/shipLoadout.ts` or extend `combatFit.ts`) so the preview can never drift from the real install result. Unit-test that installing the candidate for real (`fitEquipment`) then reading the ship equals the previewed candidate readout.

## 7. Responsive strategy

ONE component, two presentations, no `matchMedia` code-fork where avoidable:
- Roster + equip board reflow via CSS grid/flex (the loadout board's `board` grid collapses to single-column on narrow).
- Install flow: on wide viewports the list and the both-card compare render together (master-detail in one pane); on narrow, the compare is a second step (drill). Prefer a CSS-driven show/hide keyed to a container/width breakpoint over duplicated markup; if a JS breakpoint is unavoidable, one shared reactive drives both, never two code paths.
